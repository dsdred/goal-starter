## ⚠️ Current tracked debt — ADR 017 lifecycle remediation (recorded by D4, 2026-09-24)

> Tracked here, deliberately **not solved** by D4. Slice evidence, BF/RB statuses and the "program not complete" statement live in [ROADMAP.md](ROADMAP.md) (P0 → ADR 017 corrective slices + remediation register). Everything below is genuinely remaining debt or an open decision — not a duplicate of a resolved finding, and not fixed by writing it down.
>
> **On the `F-*` numbering (recorded by D6.1):** there is **no F-3** in this repository and none was ever removed — `git log --all -S"F-3"` finds no such token in any tracked file or commit message on any ref, and F-1 / F-2 / F-4 were all introduced together by D4. The series therefore originates from an external review register that the repository cannot reconstruct; the gap is not a lost finding, and **no F-3 defect is being asserted or invented here.**

- [ ] **Terminal-controller metadata retention (BF-07 aspect — hygiene-with-cost).** Once a process terminates, its `InstanceController` stays registered in the Supervisor — together with its preallocated `LogStore` (`internal/process/log_store.go`, capacity from `NewLogStore`) — until explicit cleanup (`POST /api/v1/instances/cleanup`) or the GoAl process ends. No automatic TTL / LRU / cap / background eviction exists. This is **metadata retention, not** an established process/goroutine/slot leak: the concurrency slot is released during terminal finalization. Any future bounded-retention design needs its own task and an eviction rule that can never select a controller whose record still backs a documented restart capability.
- [ ] **Durable historical `InstanceID` restart (open product/architecture decision — not a defect).** The current contract is **process-scoped** (documented in `docs/API.md`): restart of a terminal `InstanceID` works while its controller remains registered in the running GoAl process and its history record has not been explicitly cleaned; it is not guaranteed across a GoAl process restart, and cleanup removes the capability. Cross-restart durability would require reconstructing restart-capable controllers from history records — a separate product/architecture decision behind an ADR, not a correction.
- [ ] **F-1 — whole-set cleanup reconciliation needs re-review if a second production record-deletion path appears.** `Supervisor.ForgetCleanedControllers` (`internal/process/supervisor.go`) reconciles the registry against the repository's live record set. That is safe under the invariant recorded in ADR 017 §"Cleanup and Registry Reconciliation Invariant": `JSONRepository.DeleteTerminalInstances` (called only from `InstanceService.DeleteTerminalInstances`) is currently the only production path that removes a `LaunchInstance` record while the Supervisor is alive — the per-ID deleters `DeleteInstance` / `Delete` / `DeleteLaunchInstance` have zero production callers. Introducing another deletion path (per-instance delete, cascade, import overwrite, a retention job) invalidates the "a safe terminal controller without a durable record is attributable to explicit cleanup" inference and requires re-reviewing the whole-set design.
- [ ] **F-2 — missing deterministic retry regression (the implementation is already convergent).** `InstanceService.CleanupInstances` runs `Supervisor.ForgetCleanedControllers` **after a successful `DeleteTerminalInstances`, regardless of the delete count**, and the reconciliation derives its candidates from "registered controller whose id is absent from `store.List()`" rather than from that count — so a retry whose deletion removed zero rows still converges. **There is no `deleted == 0` short-circuit** (the earlier wording of this entry claimed one, and it was wrong). What is missing is a single deterministic regression pin for the chain: delete succeeds → reconciliation `List` fails → the request reports a reconciliation failure → retry deletes zero → reconciliation runs again → the safe terminal controller is removed. Each half is pinned separately today (`TestD3Cleanup_StoreReadFailureKeepsRegistry`, `TestD3Cleanup_RepositoryFailureKeepsRecordAndController`, and the `deleted == 0` repeat assertion in `TestD3Cleanup_SuccessRemovesRecordAndController`); only the cross-attempt chain is unpinned. Coverage debt, not a defect.
- [ ] **D5-02 chain-coverage debt — three invariants proven only by composition.** No single end-to-end test exists for: (a) `KillOrphan → durable stale → AdmitAndStart` on the same ModelID succeeds (`finishKill`'s `stale` write and the `stale`-does-not-block-fence predicate are each pinned, but not in one run); (b) `POST /api/v1/models/{id}/start → 409 orphan` through the real handler (the fence and the error mapping are pinned separately, and the mapping test drives the same `writeLifecycleError` the handler uses); (c) an orphan-specific model autostart skip (autostart's duplicate guard and failure-continues are pinned; `autostartModels` has no orphan-specific branch to test — the deny comes from `orphanFence`). See ADR 017 §"Concurrency / Regression Test Inventory" for the per-row mapping. Non-blocking coverage debt; must not block Manual Owner Acceptance.
- [ ] **F-4 — D3 forensic observations, recorded as observations and NOT confirmed defects.** (a) The starting-persist failure path removes the controller from the registry by `InstanceID` rather than by controller identity; (b) a pre-existing persistence write happens while the controller/instance lock is held. Current `InstanceID` values are process-unique (model ID + nanosecond timestamp + atomic sequence), so neither has demonstrated harm. Each needs its own targeted forensic before being classified as a defect.
- [ ] **D2 deferred A — `waitFileRewrite` observation window.** `internal/application/restart_reresolve_test.go` detects the durable rewrite by mtime on a 50 ms poll and does not fail on timeout, so a truncate/write inside the filesystem timestamp granularity can be missed. Test-harness hardening debt, not a production defect. *(Recurred 2026-09-30: attempt 1 of CI run `36727279521` for `2d30d97d80a915f362ffea2bccf099edf53e925e` failed in the preliminary plain `go test ./...` on `--- FAIL: TestRestartInstance_ReresolvesCurrentModelArgs` → `restart_reresolve_test.go:141: child did not receive current Model.Args: ""` — the same truncate/read window, this time with an empty read. It did **not** reproduce on the one Owner-authorized same-SHA rerun, and no repository change was made to it.)*

CI-shape debt (surfaced while adjudicating the D2 same-SHA rerun). *Recurred 2026-09-30 exactly as described: in attempt 1 of CI run `36727279521` (`2d30d97d80a915f362ffea2bccf099edf53e925e`) step 4 "Run tests" failed on the D2-deferred-A assertion above and step 5 "Run tests with race detector" was reported **skipped**, so the published SHA briefly had no race evidence at all; it exists only from the authorized same-SHA rerun (attempt 2). - [ ] **D2 deferred C — `ErrInstanceNotFound` textual rendering changed by sentinel wrapping.** D2 made the not-found case carry the sentinel (`fmt.Errorf("%w: %s", ErrInstanceNotFound, id)`), which changed the rendered message text at the affected sites. No production consumer of the old rendering was found; residual risk only for consumers outside the repository that match on text. Wire status/`code`/`error` are unchanged.
- [ ] **BF-02d — latent `ListInstances` error swallowing in pipeline helper paths.** `PipelineService.hasActiveOwnedInstances` (`internal/application/pipeline_service.go`) returns `false` when the store read fails, so a structural pipeline edit or delete that is gated on "no active owned instances" can pass on a transient read error. ## ⚠️ Security debt — client-origin identity and forwarded headers (recorded 2026-09-30, from ADR 019 §D20 / Owner decision P5)

> Recorded here because [ADR 019](docs/adr/019-native-https-secure-origin.md) deliberately does **not** decide it: Owner decision **P5** classifies proxy identity as **separate** security/technical debt, and ADR 019 §Open questions 2 names an authorized BACKLOG boundary as the place it must be tracked. Nothing below belongs to any ADR 019 implementation slice, and shipping TLS does **not** close it. ADR 019 §D20 remains in force meanwhile: GoAl honors no `X-Forwarded-Proto` / `Forwarded` / `X-Real-IP` for security decisions, so behind a TLS-terminating proxy the session cookie stays non-`Secure`.

- [ ] **PROXY-01 — the server contains two divergent client-identity rules, one of them attacker-controlled (class C security / technical debt; fixing it needs a class E trust-boundary design).** Proven from current bytes:
  - **Trusted-peer rule — correct for security decisions.** `clientIP` (`internal/webui/handlers/helpers.go:149-154`) derives the address from `r.RemoteAddr` only, with its doc comment at `:148` stating that `X-Forwarded-For` / `X-Real-IP` are "intentionally not trusted (spoofable)". Its consumers are precisely the accountability paths: audit `SourceIP` (`internal/webui/handlers/auth.go:100`, `auth.go:119`, `internal/webui/handlers/helpers.go:183`) and the login rate limiter (`internal/webui/handlers/routes.go:312`, rationale comment `:306-309`), pinned by `internal/webui/handlers/routes_rate_limit_test.go:114` / `:124` ("spoofed X-Forwarded-For must not bypass the limiter"). `ROADMAP.md` records the same rule as an accepted P0 decision.
  - **Header-trusting rule — log-only today, and duplicated.** `getClientIP` exists **twice, independently**: `internal/webui/logger/logger.go:66-77` and `internal/webui/middleware/logging.go:55-67`. Both return `X-Real-IP` when present, else the **first** element of `X-Forwarded-For`, and only then fall back to the TCP peer — so the address printed in the `http: METHOD PATH STATUS …` request log (`internal/webui/middleware/logging.go:30`) is entirely client-chosen. Its only consumers are log statements (`internal/webui/logger/` and the logging middleware), so no security decision currently reads it.
  - **Why this is debt rather than something to leave unnamed:** the two rules live one package apart and the spoofable one is duplicated, so the next consumer that needs "the client address" has a real chance of selecting the wrong helper; and while the limiter stays correct, the audit trail and the request log record **different** addresses for the same request, which weakens the ADR 007 accountability record during an incident. The fix must not simply delete the header reads: behind a LAN or TLS-terminating proxy the TCP peer **is** the proxy, so plain-HTTP-only deployments would lose whatever log fidelity the headers give them today.
  - **Required direction before any change (class E — design gate first, then its own slices).** Security decisions must never be derived from forwarded headers without an explicit **trust-boundary design**: an operator-declared trusted-proxy boundary (configured list, or a documented decision that GoAl never has one), the RFC 7239 `Forwarded` vs `X-Forwarded-*` choice and which chain element is authoritative, whether audit `SourceIP` and the request log must converge on a single derived value from one shared helper, the interaction with ADR 019 §D20 (a proxy deployment keeps the cookie non-`Secure`, so a trusted-proxy design must not imply a secure context), and the effect on ADR 007 secret-safety and retention rules. Owner decisions P4/P5 constraints stay in force until that gate decides; this entry authorizes **tracking only**, not implementation.

It became its own task because the Owner ruled that the forward-version guard must not be mixed with ADR 020 ([ADR 020](docs/adr/020-services-catalog.md) §Context **FD-6**), and because the revised catalog design no longer bumps the schema at all (ADR 020 §D5) — which would otherwise have made the guard read like a catalog prerequisite. The finding, its byte evidence and its required resolution are carried into `SCHEMA-VER-01` unchanged in substance; this pointer stays so the origin of the task and the date of the move are not lost.
- [ ] **CATALOG-DEP-06 — the maintained raw-key detector cannot see a new top-level i18n group, so a whole vocabulary could ship untranslated while every gate stays green (class C coverage gap, pre-existing and wider than the catalog).** Two blind spots compose. **Static:** `TestI18nDictionariesParity` scans `data-i18n` attributes (`internal/webui/server_test.go:69`) and literal `t('key')` call sites (`:73`), so a label assembled at runtime is outside the parity check entirely. **Runtime:** the browser suite's raw-key regex is anchored to an **allowlist of top-level prefixes** — `app|auth|blocked|common|confirm|conn|err|history|instances|logs|models|nav|pipelines|portable|runtimes|settings|sidebar|wizard` (`tests/browser/i18n.cjs:167`, consumed by the DOM scan at `:166-201`) — so a key from a group outside that list is invisible even when it renders literally into the page. The runtime miss-detection itself exists (`internal/webui/static/app.js:35`, `:42`, exposed as `window.i18nMissing` at `:2923` — shifted from `:2689`'s +1 insertion ADR 018's Slice 1 made in the blocked-reason table on 2026-10-04) and the suite asserts it stays empty, but only for keys a composed label actually requests. **Consequence:** introducing a new top-level group is exactly the case in which an unlocalized UI passes both gates. **Required direction:** either keep new vocabulary inside an allowlisted group (ADR 020 §D6 places the icon labels under `models.icon.<id>` **inside the existing `models.` group** for exactly this reason — so rev 4 creates **no** new top-level group and no catalog instance of this gap is live today; the group's parity must be checked against the **supported** set rather than literal `t('key')` sites alone, because a retired identifier renders and is accepted on write while carrying no literal call site) or extend `i18n.cjs:167` in the same change that introduces a group; the durable fix is to replace the prefix allowlist with a structural assertion (any dotted `group.key.sub` token visible in the DOM that resolves to no dictionary entry is a failure) — **and if that assertion is ever written it must scope to label sites**, because an unscoped one would fire on a service's legitimate `description` text whenever that user data happens to contain a dotted token. The catalog design only discovered this gap, it is not caused by it, and closing it is not part of any catalog slice.

## ⚠️ Storage forward-compatibility — `SCHEMA-VER-01` (promoted out of the services-catalog findings section on 2026-10-03, per the Owner's ruling **FD-6** of [ADR 020](docs/adr/020-services-catalog.md))

> A **standalone** technical task, deliberately **not** part of ADR 020: the Owner instructed that the unsupported-storage-version problem be kept separate and its fix not mixed with the catalog design (ADR 020 §Context FD-6, §D5 honest consequence, §Sequencing item 5). It is valuable independently of the catalog — **any** future schema change inherits it — and no catalog slice may absorb it by default. ADR 020 neither fixes it, nor narrows it, nor gates on it; the ordering question that used to sit here (**Q22**) was **answered by the Owner on 2026-10-03 — «SCHEMA-VER-01 не блокирует каталог»** — so no catalog slice waits on this task, and this task is not scheduled by ADR 020 either: it runs whenever the Owner schedules it, before or after the catalog.

- [ ] **SCHEMA-VER-01 — the durable repository file has no upper-bound schema-version guard, so a future-versioned file is silently downgraded on the next save (class C latent debt today; blocker-class for any schema bump).** The load path parses `schema_version` (`internal/storage/repository.go:231-244`) and then branches on **`<=5`** (`:246`), **`==6`** (`:250`) and **"everything else"** (`:254-272`) — the last branch unmarshals straight into a struct of exactly four collections, so a higher number is not an error, it is simply *treated as current*, and any key the struct does not know is discarded by `encoding/json` without a word. `writeUnified` then hard-codes `"schema_version": 8` with those same four collections (`:528-535`) and `SchemaVersion()` returns the literal `8` (`:552`), so the very next save rewrites the file at v8 **without the fields the newer binary wrote** — **silent data loss, no WARN, no refusal**. `tryBackup` (`:509-521`) parses `SchemaVersion` only to prove the `.bak` is valid JSON and never compares it; it is reached only when the read or the parse *fails* (`:225`, `:237`), so it offers no protection here and could in principle resurrect a stale file behind a future refusal. The portable bundle already demonstrates the opposite, deliberate posture: an unknown bundle **version** fails closed with `ErrUnsupportedVersion` (`internal/application/portable/portable.go:130-132`). **Nothing is broken today** — no file above v8 exists — which is why this is registered as debt rather than a defect; it becomes live the moment the first bump ships. Note also, on the same reading path, that `docs/LIMITATIONS.md:105` describes the tracked field as `version` while the actual JSON key is `schema_version` (`repository.go:233`, `:530`) — worth correcting whenever that file is next touched, and it does not change the substance of what that section states. **Required resolution — the Owner chooses between two options, and silent, unlogged loss is not an acceptable third:** (a) add a fail-closed guard rejecting `schema_version > SchemaVersion()` with a clear error and **zero writes** (mirroring the bundle), with the `.bak` fallback explicitly proven not to resurrect the newer file, plus a test pinning the refusal, or (b) accept the downgrade and document it in `docs/LIMITATIONS.md` + the user guides, including a WARN on the load path. `docs/LIMITATIONS.md:103` ("No schema versioning framework") is this task's existing home in the documentation. This is valuable independently of the catalog: **any** future schema change inherits it, which is exactly why it was promoted to its own task on 2026-10-03 (FD-6) instead of being bundled into a catalog slice's scope.
- [ ] **SCHEMA-VER-02 — the version number is not a coverage signal: unknown-*field* loss already happens between binaries that share it, so option (a) above is necessary but not sufficient (class C, same task family; discovered while proving ADR 020 §D5 needed no bump).** Two binaries at the **same** literal `schema_version` can already carry different field sets: commit `3347b2b` (2026-09-12) added persisted fields (`pipeline_entry_id`, pipeline entry `id`, `EnvPatchOp`) without touching `schema_version` — `git log -S'schema_version": 8' -- internal/storage/repository.go` returns only `9f0ecf5` (2026-08-31) — and [ADR 013](docs/adr/013-pipeline-repeat-models-ux-polish.md) §D6 states "No schema version bump (stays v8)" (`:99`, with the backward-compatibility proof at `:101`), which the Owner ratified as decision item (5) (`:214`), and `internal/storage/pipeline_test.go:523` asserts the literal `8` precisely so that it does not move. The read path's final `else` branch unmarshals into a fixed struct (`internal/storage/repository.go:254-272`), so a field a binary does not know is discarded by `encoding/json` without an error or a WARN, and the next save rewrites the file without it. **A `schema_version` upper-bound guard is blind to this by construction — the hazard is unknown *fields*, not a higher *number*.** **Required direction:** decide the unknown-field posture separately from SCHEMA-VER-01 (the same two shapes apply: refuse with a clear diagnostic, or accept and document the loss with a WARN on the load path), and record which project decisions already rely on it — ADR 013 §D6 and ADR 020 §D5 both do. Registered here so SCHEMA-VER-01's option (a) is never sold as a complete fix.
