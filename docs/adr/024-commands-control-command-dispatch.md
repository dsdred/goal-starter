## Context

### What is being contracted

GoAl 3 priority **#1 — Commands** ([ROADMAP.md](../../ROADMAP.md) §GoAl 3, 2026-11-16) introduces a **unified command-execution surface** over the existing services: a command *describes* and *initiates* an action and *delegates* execution to the service that already performs it. The first slice (**CMD-1**, [BACKLOG.md](../../BACKLOG.md) **G3-COMMANDS-01**) is the thinnest possible vertical: **one command (`model.start`), one dispatch point, delegation to the existing `InstanceService.StartModel`, a minimal API contract, and tests.** It exists to prove the "describe + delegate, do not duplicate" pattern — no second supervisor, no duplicated ADR 017 arbitration, no duplicated ADR 016 / 021 lifecycle.

### Why this is ADR-first (the significance test)

[AGENTS.md](../../AGENTS.md) gates **significant work** behind `ROADMAP → ADR → contract → implementation → tests → acceptance → docs reconciliation`, and lists **"public API"** and **cross-cutting architecture** among the triggers. CMD-1 is a **new public HTTP endpoint** (`POST /api/v1/commands/execute`) and the **seed of a cross-cutting command surface** on which Stage 2 (a persisted command entity) and Stage 3 (agent commands over MCP + scoped tokens) will build. The command *model, vocabulary, error normalization and audit semantics* are therefore a durable contract, not a one-off. The [BACKLOG.md](../../BACKLOG.md) **G3-COMMANDS-01** row already records this: the full Commands contract is "**class E**, scoped minimally, and **opened only when this first slice is authorized for implementation**."

## Decision

The command is a **thin dispatch primitive at the HTTP edge**. It names an action and routes it to the service that already performs it. The sealed invariants are **D-1 … D-7** (CMD-1, `model.start`), extended by **D-8 … D-10** to the full Stage 1 six-command vocabulary (Stage 1 completion, 2026-11-17), by **D-11** to the per-component `instance.*` commands (G3-RES-01 API exposure, 2026-11-17), and by **D-12** to the per-component `instance.start` command (G3-RES-01 per-component Start, 2026-11-18).

- **D-1 — Thin dispatch, not a controller.** A new `CommandsHandler` (HTTP edge) maps a command name to an existing application-service method. It holds **no** `*process.Supervisor` reference, **no** lifecycle logic and **no** arbitration code of its own — the entire lifecycle is reached only by delegating to `InstanceService.StartModel` (→ `Supervisor.AdmitAndStart`). This is the single non-bypassable boundary: **there is no second supervisor, no second arbitration path, no lifecycle duplication.**

- **D-2 — `POST /api/v1/commands/execute`, `requireAuthCSRF`.** One mutating route for all Stage 1 commands, wrapped by the same `requireAuthCSRF` boundary every other mutating route uses ([routes.go](../../internal/webui/handlers/routes.go) `:283`). A command executes with the caller's own session + CSRF token; there is no weaker or separate auth path, and no LAN exposure.

- **D-3 — Closed Stage 1 vocabulary, exact-match.** The Stage 1 command set was opened at **{ `model.start` }** (CMD-1) and is **extended by D-8** (Stage 1 completion, 2026-11-17) to the full closed set of six: **{ `model.start`, `model.stop`, `model.restart`, `pipeline.start`, `pipeline.stop`, `pipeline.restart` }**. Matching is exact, case-sensitive string equality; any other `command` value is an **unknown command** (D-6). Each command re-uses the **same** dispatch point (`POST /api/v1/commands/execute`) and the same `requireAuthCSRF` boundary (D-2). The closed set is **further extended by D-11** (G3-RES-01) with the per-component `instance.stop` / `instance.restart` commands, and by **D-12** (G3-RES-01 per-component Start) with the per-component `instance.start` command; it remains a closed, exact-match set.

- **D-4 — Body & identifiers.** Request body is `{ "command": string, "targetId": string }`. `targetId` is the **model ID** for `model.start` — the same identifier the existing route carries in its path. An empty `command` or empty `targetId` is a **malformed request** (400). The command carries **no** other parameters in Stage 1.

- **D-5 — Success & lifecycle errors are identical to `model.start`.** On success the endpoint returns the **same** `200` body the existing `model.start` returns — the started instance entry (`domain.ToStorageEntry(inst)`, environment nulled). Every lifecycle failure is mapped through the **existing** `writeLifecycleError` classifier, so `model.start` via `/commands/execute` yields the **same** status + `code` as `model.start` via `/models/{id}/start`: 409 `launch_in_flight`, 409 `orphan`, 503 `shutting_down` / `launch_aborted`, 500 `launch_persist_failed` / `termination_unconfirmed` / `rollback_failed`. **No lifecycle code path is re-implemented; the command adds zero lifecycle semantics.**

- **D-6 — Command-surface errors are new bounded codes (the one place the surface differs).** Two conditions are inherent to the command surface and have no `model.start` analogue, so they get their own bounded tokens rather than leaking a 500:
  - **unknown command** → `400` `{ "code": "unknown_command", "error": … }`. A new `CodeUnknownCommand` bounded code (the closed set of Stage 1 commands is the reference; the message names the rejected value, never a stack trace).
  - **unresolvable target** (the model does not exist) → `404` `{ "code": "not_found", … }`. This is a **deliberate improvement** over the current `model.start` behavior for a non-existent model, which today falls through to **500** (see "Present bytes"). It changes **only the new endpoint's** error classification: the existing `POST /api/v1/models/{id}/start` route and `InstanceService.StartModel` are **not** modified, so `model.start` semantics on the existing route are unchanged (constraint respected). The command layer re-runs the same resolution and reports the not-found as a bounded 404 before delegating.
  - A new bounded code for unknown command, and the 404 reclassification, are **additive**: they touch only the new handler's error path and the shared `errors` code set (one new constant). No existing route's mapping changes.

- **D-7 — No new audit event in Stage 1; unified control-action audit is a separate non-blocking follow-up (amended 2026-11-17).** CMD-1 introduces **no** `command.execute` audit of its own. `model.start` via `/commands/execute` carries the **same** audit behavior as `model.start` via `/models/{id}/start` today — which is **none** (see "Present bytes": the model route emits no `logAudit`). Rationale (Owner decision 2026-11-17): the **same** control action must have **one** audit semantic regardless of entry point; auditing only the new endpoint would fork that semantic, so the unified control-action audit is **not** introduced piecemeal in this slice. It is registered as a **separate non-blocking follow-up** ([BACKLOG.md](../../BACKLOG.md) **G3-AUDIT-01**), which will give every control action one entry-point-independent ADR 007 record. CMD-1 **does not disable or bypass any existing audit**: the `instance.*` / `pipeline.*` ADR 007 events (`audit.go:55-64`) are untouched. This is the strict-parity form of the original D-7 proposal; the dispatch (D-1…D-6) is unchanged. **Stage 1 completion (D-8 … D-10, 2026-11-17):** parity is extended command-by-command, so a command's audit behavior is exactly that of its per-object route — the `model.*` commands emit **no** audit event (the model routes are unaudited today), and the `pipeline.*` commands emit the **same** ADR 007 `pipeline.start` / `pipeline.stop` / `pipeline.restart` control-action event (same bounded counters, same user attribution, identifier-only) that the `POST /api/v1/pipelines/{id}/…` routes emit. In every case the new surface introduces **no** `command.execute` record and disables or bypasses **no** existing `instance.*` / `pipeline.*` event — the single-audit-semantic question (which entry point owns the record for a given action) remains owned by the non-blocking follow-up [BACKLOG.md](../../BACKLOG.md) **G3-AUDIT-01**.

- **D-8 — Stage 1 vocabulary completion (added 2026-11-17; extends D-3).** The remaining five Stage 1 control commands are added to the closed set — `model.stop`, `model.restart`, `pipeline.start`, `pipeline.stop`, `pipeline.restart` — each dispatched from the **same** `CommandsHandler` and the **same** `POST /api/v1/commands/execute` route, each **delegating** to the existing service that already performs the action. This adds **no** second supervisor, **no** second arbitration path, **no** lifecycle or ownership logic of its own (D-1 holds for all six): `model.stop` / `model.restart` delegate to `InstanceService.StopInstance` / `RestartInstance` (→ `Supervisor.Stop` / `RestartWithLaunch`); `pipeline.start` / `pipeline.stop` / `pipeline.restart` delegate to `PipelineService.Start` / `Stop` / `Restart`. The existing per-object routes and services are **not** modified (C-6).

- **D-9 — `targetId` is the object ID (added 2026-11-17; extends D-4).** The body is still `{ "command": string, "targetId": string }` (D-4). `targetId` is the **model ID** for `model.*` commands (the same identifier the `POST /api/v1/models/{id}/…` routes carry in their path) and the **pipeline ID** for `pipeline.*` commands (the same identifier the `POST /api/v1/pipelines/{id}/…` routes carry in their path). An empty `command` or `targetId` is a 400 (D-4). The command carries **no** other parameters.

- **D-10 — Per-command success / lifecycle-error / audit parity (added 2026-11-17; the Stage 1 form of D-5/D-6/D-7).** Each command returns the **same** success body and the **same** status + `code` as its per-object route, because it is the same delegated service call with the same classifier applied:
  - `model.start` — the `200` instance-entry body (environment nulled) and the D-5 lifecycle mapping (unchanged from CMD-1).
  - `model.stop` — the `200 { "status": "stopped" }` body the `models/{id}/stop` route returns; a `pending` launch of the model is `409 launch_in_flight`; every live instance is stopped through the single ADR 017 boundary.
  - `model.restart` — the `200 { "status": "restarted" }` body the `models/{id}/restart` route returns; the whole in-flight target set is preflighted first (`InstanceService.PreflightRestart`, ADR 017 D1) so no instance is mutated and then left un-restarted, then each target is restarted through the single ADR 017 boundary.
  - `pipeline.start` / `pipeline.stop` / `pipeline.restart` — the **same** aggregate result body and the **same** group-failure status + `code` (`groupFailureClass`: 500/503/409 with the existing `pipeline_*` tokens) that the corresponding `pipelines/{id}/…` route returns, including the same ADR 007 control-action audit event on success and on an incomplete group (D-7 parity).
  - The **one** command-surface distinction (D-6) is preserved for all six: an unresolvable `targetId` (a model/pipeline that does not exist) is a bounded **404 `not_found`** on the command surface, whereas the existing routes (unchanged) fall through to their previous behavior. `unknown_command` (400) and empty-field (400) are unchanged. No lifecycle or ownership code path is re-implemented; the command adds **zero** lifecycle semantics for any of the six.

- **D-11 — Per-component (`instance.*`) control commands (added 2026-11-17; G3-RES-01 API exposure).** Two commands are added to the closed set (D-3): **`instance.stop`** and **`instance.restart`**, each dispatched from the **same** `CommandsHandler` and the **same** `POST /api/v1/commands/execute` route, each **delegating** to the existing service that already performs the action — **no** second supervisor, **no** second arbitration path, **no** lifecycle or ownership logic of its own (D-1): `instance.stop` → `InstanceService.StopInstance` (→ `Supervisor.Stop`); `instance.restart` → `InstanceService.RestartInstance` (→ `Supervisor.RestartWithLaunch`), the single ADR 017 boundary.
  - **`targetId` is the InstanceID** (extending D-9): for `instance.*` the target is the **instance** identifier — the same one the per-object `POST /api/v1/instances/{id}/…` routes carry in their path, and the one the ADR 017 arbitration and the `pipeline.start` result expose per component. A pipeline component is one owned instance (launched via `Supervisor.AdmitAndStart(…, PipelineOwner)`); its operational identity is its InstanceID, and a live **or** a retained terminal instance is a resolvable target (the same resolvable set the per-object instance routes operate on).
  - **Parity (D-7/D-10 form):** `instance.stop` returns the **same** `200 { "status": "stopped" }` body and `instance.restart` the **same** `200` instance-entry body (environment nulled) that the per-object `/instances/{id}/stop` / `/instances/{id}/restart` routes return, and each emits the **same** ADR 007 `instance.stop` / `instance.restart` control-action event (carrying `instance_id`, the command's single target) that those routes emit (identifier-only; no model-name or sibling identity added). The one command-surface distinction (D-6) is preserved: an unresolvable instance is a bounded **404 `not_found`**.
  - **Why `instance.*` and not `model.*` (the proven necessity, G3-RES-01):** `model.stop` / `model.restart` are **model-scoped fan-out** — they iterate **every** live / in-flight instance where `inst.ModelID == modelID` and stop/restart each one. A repeatable model (ADR 013) may hold several such instances at once (e.g. the same model as two entries of one pipeline), so a `model.*` command **cannot name a single component**. Controlling one component — stopping exactly the instance a pipeline entry owns, without touching its siblings or any other copy of the same model — is instance-scoped by definition, and so requires a distinct `instance.*` command. Reusing `model.*` here would fan out over the wrong set.
  - **Release mechanism (no measurement claim):** stopping a component terminates its process group / Job Object (ADR 001) and the single `cmd.Wait` owner (ADR 016) confirms the exit — this is how the component's resources are released. **Measured VRAM accounting is out of scope** and belongs to **G3-RES-02**; this slice makes **no** measured VRAM-release claim and adds no telemetry.
  - The pipeline-wide commands (D-8) and the existing per-object `model` / `pipeline` / `instance` routes are **unchanged** (C-6).

- **D-12 — Per-component `instance.start` (added 2026-11-18; G3-RES-01 per-component Start).** A third per-component command is added to the closed set (D-3): **`instance.start`**, dispatched from the **same** `CommandsHandler` and the **same** `POST /api/v1/commands/execute` route (D-2), with **`targetId` = the InstanceID** (D-9/D-11 form). It starts exactly **one** terminal component back up, on its **same InstanceID**, without touching siblings or other copies of the same model.
  - **Command-only action (no per-object route twin).** There is no `POST /api/v1/instances/{id}/start` route in the product: per-object Start does not exist, and D-12 deliberately does **not** add one. The only existing instance-start surface — `POST /api/v1/instances/start` (model-scoped, **mints a new instance** via `AdmitAndStart`) — is a different action and stays **byte-for-byte unchanged** (C-6). Consequently D-12's audit has no per-object parity twin to mirror (see below).
  - **Semantics — same ID, fresh configuration.** The target is an **existing** terminal instance whose controller is still registered in this process (the same resolvable set `instance.restart` operates on; process-scoped, ADR 017). It re-launches through `InstanceService.StartInstance` → `Supervisor.StartInstance` → the single ADR 017 boundary with a **freshly resolved** launch configuration (same ownership-aware resolution as `instance.restart`: model-scoped relaunch or entry-Args relaunch, runtime re-resolved). **Ownership is derived from the TARGET instance, never from the caller** (ADR 017). The same-ID invariant holds exactly as for restart: the **InstanceID**, the **persisted record**, and the `PipelineID`/`PipelineEntryID` attribution are preserved; a new PID is minted; **no second instance record is created and `Supervisor.AdmitAndStart` is never used.**
  - **State gate (atomic, not a pre-check).** The permitted target states are **`exited` / `failed` only**. The gate is the ADR 017 **start gate** — the target precondition of the newly ratified sealed claimant **`claimStartExisting`** — evaluated **inside `Supervisor.arbitrate` under the per-ModelID `arbLock`, in the same atomic section and before the same publication** as the restart gate (ADR 017 amendment, 2026-11-18). A service- or handler-level pre-check was examined and **rejected** by the Owner: it is not atomic with the reservation publication, so a state observed as `exited` before the check could be `running` by the time the claim publishes, and a start would then stop-and-relaunch a live generation. The sealed gate makes that interleaving impossible:
    | Target state at the gate | Outcome |
    |---|---|
    | `exited`, `failed` | admit → same-InstanceID spawn, new PID |
    | `running`, `stopping` | refuse `409` `already_running` (new bounded token, `ErrAlreadyRunning` sentinel; **no mutation of the live generation**) |
    | `pending`, `starting` | refuse `409` `launch_in_flight` |
    | `stale`, `orphan` | refuse `409` `not_restartable` (in-memory) / `409` `orphan` (repository fence); in ordinary operation a `stale` ID is `404 instance_not_found` (no registered controller) |
    | supervisor shutting down | `503` `shutting_down` / `launch_aborted` |
    | unresolvable `targetId` | `404` `not_found` (D-6, command surface) |
  - **Arbitration reuse (no second boundary, no bypass).** `claimStartExisting` is the **third** sealed claimant mode on the **existing** boundary (`claimNewAdmission`, `claimRestartExisting`, `claimStartExisting`). It shares the restart claimant's machinery verbatim: owner derivation from the target, `scanConflicts` (exact-InstanceID self-exemption, ADR 013 compatibility matrix), the repository orphan fence, the same controller-local reservation publication under `launchMu`, the same generation-bound single-use spawn claim, and the same `restartWithRefresh` lifecycle tail. Consequences: a **concurrent second `instance.start`** on the same target is refused `409 launch_in_flight` (the first start's reservation is published before the second's gate runs); a **start vs. restart race** on the same target resolves to exactly one admitted operation (first published reservation wins); a **start vs. `pipeline.start`** race is arbitrated by the same matrix (a same-model in-flight or reservation-visible sibling is conflict-checked exactly as for any other launch); and a **start vs. stop** race cannot stop the target — a `stopping` gate state is `already_running`, and a stop that begins after the start's publication is ordered after the new generation by the per-instance `lifecycleMu`. **No other ADR 017 sealed invariant changes; ADR 010 / ADR 015 are unchanged; `pipeline.start` semantics are unchanged.**
  - **Audit (separate event, identifier-only).** `instance.start` emits the ADR 007 **`instance.start`** control-action event carrying **`instance_id` only** (no `model_id`, no sibling identity); on refusal the bounded lifecycle `error` token is added, never raw error text. It does not disable or bypass any existing `instance.*` / `pipeline.*` event; the entry-point-independence question stays with **G3-AUDIT-01**. (The model-scoped `POST /api/v1/instances/start` route keeps its own existing `instance.start` records with `model_id` + `instance_id`; the two share only the event name.)
  - **Pipeline UI (precise attribution only).** The pipeline chips offer a per-component **Start** **only** when the entry → instance attribution is precise (by `pipeline_entry_id`) and the single attributed instance is `exited` / `failed` (a running component keeps Stop/Restart, D-11). An entry **without** a resolvable instance keeps the **pipeline-wide Start** (the chip hint), exactly as before — the fallback never gains a per-component button, because a `model_id` fallback match could address a sibling copy of a repeatable model.
  - **Clarification — retained history (dated 2026-11-24, v2.3.0 RC defect fix).** The clause above predates the multi-cycle observation that a precisely attributed entry accumulates **retained terminal records** with every pipeline-level start (D-11 resolvable-set semantics; supervisor retention — no TTL, no eviction). "The single attributed instance" described the record shape as observed at ratification; the ratified contract obligation is **precise attribution**, not history size. The chip resolves the entry's **current** instance deterministically: a **single `running`** attributed instance wins (Stop/Restart); otherwise the **newest** attributed `exited`/`failed` record wins (Start, same-ID, D-12), ordered by `started_at`, then `created_at`, then InstanceID; **more than one live** attributed instance is ambiguous and yields **no** per-component control (never an arbitrary target). A transitional-only live (`starting`/`stopping`) instance keeps the no-button behavior; the precise-attribution requirement and the legacy/fallback no-button rule are **unchanged**. This clarification moves no backend command semantics, state model, or pipeline-level control.
  - **No measurement claim.** Starting a component releases nothing and measures nothing: this slice makes **no** VRAM accounting claim (**G3-RES-02**).

## Security analysis (no bypass)

- **Auth:** identical `requireAuthCSRF` boundary as every other mutating route; no new trust relationship, no unauthenticated or LAN-exposed path.
- **CSRF:** command execution is a state-changing POST behind the session CSRF token — the same protection as `model.start`.
- **Arbitration / lifecycle:** reached **only** through the application services → the ADR 017 boundary (`AdmitAndStart` for new instances, `Stop`, `RestartWithLaunch`, and — D-12 — `StartInstance` for a terminal instance's same-ID start). The command layer never calls the supervisor, never mints a spawn claim, and never short-circuits the conflict/orphan/shutdown/start-gate checks.
- **Error surface:** bounded tokens only (D-5/D-6); no raw process text, no internal detail, no new information channel.

## Acceptance (obligations for the implementation slice, NOT run here)

- **C-1** `POST /api/v1/commands/execute` with `model.start` + a valid, startable `targetId` returns the same 200 instance-entry body as `POST /api/v1/models/{id}/start`.
- **C-2** unknown `command` ⇒ 400 `unknown_command`; empty `command`/`targetId` ⇒ 400.
- **C-3** non-existent `targetId` ⇒ 404 `not_found`.
- **C-4** an in-flight launch of the target ⇒ 409 `launch_in_flight` (same token as `model.start`).
- **C-5** unauthenticated ⇒ 401; authenticated without a valid CSRF token ⇒ 403.
- **C-6** the existing `POST /api/v1/models/{id}/start` route's behavior and its (current) unaudited/no-500-vs-404 distinction are **byte-for-byte unchanged**; `InstanceService.StartModel` and the ADR 017 boundary are **untouched**.
- **C-7** (per amended D-7) a command execution emits **no** `command.execute` audit record in Stage 1 (matching the unaudited model route), and **no** existing `instance.*` / `pipeline.*` ADR 007 audit is disabled or bypassed.
- **C-8** (Stage 1 completion, D-8 … D-10): the five additional commands execute and are verified — (a) `model.stop` returns the `200 { "status": "stopped" }` body and stops the model's live instances; a `pending` launch returns `409 launch_in_flight`. (b) `model.restart` returns the `200 { "status": "restarted" }` body and restarts the model's in-flight instances through the prefetched ADR 017 path. (c) `pipeline.start` / `pipeline.stop` / `pipeline.restart` return the **same** aggregate body + status + `code` as their `pipelines/{id}/…` routes (including an `already-running` outcome on a re-start) and emit the **same** ADR 007 control-action audit event (success and incomplete-group). (d) an unresolvable `targetId` for any command returns `404 not_found`; a `command` outside the six returns `400 unknown_command`; an empty `command` / `targetId` returns `400`. (e) the command surface is authenticated + CSRF-protected (401 unauthenticated, 403 without a valid token). (f) the existing model/pipeline per-object routes are **byte-for-byte unchanged** in behavior (C-6) — no CMD-1 or CMD-2 regression on the existing routes.
- **C-9** (G3-RES-01, D-11): the per-component commands are verified — (a) `instance.stop` on a running pipeline component returns `200 { "status": "stopped" }` and stops **exactly that** instance; (b) `instance.restart` returns the `200` instance-entry body (environment nulled) and the restarted instance preserves its **identity** (same InstanceID) with a new PID through the ADR 017 boundary; (c) an unresolvable instance `targetId` returns `404 not_found`; (d) each emits the **same** ADR 007 `instance.stop` / `instance.restart` control-action audit event (carrying `instance_id`, identifier-only, no model-name or sibling identity) that the per-object routes emit — and **no** `command.execute` record; (e) **single-instance scope**: with one model held as two live pipeline components (a repeatable model), `instance.stop` on one leaves the **other still running** — proving no `model.*` fan-out; (f) the command surface is authenticated + CSRF-protected (401 / 403, as C-5); (g) the existing per-object `model` / `pipeline` / `instance` routes and the pipeline-wide commands (D-8) are **byte-for-byte unchanged** (C-6). No measured VRAM-release claim is made (G3-RES-02).
- **C-10** (G3-RES-01 per-component Start, D-12): the `instance.start` command is verified — (a) on an `exited` component it returns the `200` instance-entry body (environment nulled) with the **same InstanceID** and a **new PID**, and the `PipelineID`/`PipelineEntryID` attribution is preserved (same for a `failed` component); (b) on a **running** component it returns `409` `already_running` and the running instance's PID is **unchanged** (no stop, no spawn — the absence of lifecycle side effects is asserted, not only the code); (c) `pending`/`starting` → `409 launch_in_flight`; an unresolvable target → `404 not_found`; a stale/orphan target → the bounded rejection; shutdown → `503`; (d) **concurrency**: two simultaneous `instance.start` on the same target admit **exactly one**; a start racing a restart of the same target admits at most one; a start racing a pipeline start of a same-model sibling is arbitrated by the ADR 013 matrix; (e) with one model held as two components (a repeatable model), `instance.start` on one terminal component leaves the **other component untouched** (no model fan-out); (f) each success emits exactly one ADR 007 `instance.start` event carrying **`instance_id` only** (no `model_id`, no sibling identity), a refusal adds the bounded `error` token, and **no** `command.execute` record is ever emitted; (g) the existing per-object routes, the model-scoped `POST /api/v1/instances/start`, and the pipeline-wide commands remain **byte-for-byte unchanged** (C-6); (h) the Pipeline UI offers a per-component Start **only** for a precisely-attributed `exited`/`failed` component, and an entry without a resolvable instance keeps the pipeline-wide Start hint. No measured VRAM-release claim is made (G3-RES-02).
