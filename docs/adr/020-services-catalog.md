### Why this is a design task and not a small edit

Rev 1 identified three pressures. FD-1/FD-4 dissolve two of them outright, and one survives:

1. **Storage + portable format (rev 1: a fourth collection and a version bump).** **Dissolved.** With a closed set there is no new entity, no new collection and no repository-interface change — only two optional fields on an existing entity — and D5 therefore proposes **no schema bump**, on ADR 013's own ratified precedent. The portable half was already closed by Q9 (FD-5 restates it): the initial scope touches no bundle byte, and transfer of the new fields is designed separately.
2. **The category image substrate (rev 1: no upload surface exists).** **Dissolved twice over.** Q6 had already ruled out upload in favor of built-in glyphs; FD-1 removes even the *choice* — the icon belongs to the category, and the categories are code. Nothing user-supplied is stored per category, so there is no field to validate as markup, no path to resolve, and no persistence surface to invent.
3. **Maintained browser-acceptance selectors (R1 + R4).** **Still live, and now decided.** The suite binds to the models view in two different ways, and the difference matters for what the rename can break. Card bindings are `.model-row`-class-dependent and must be retargeted when services get their own family: **13 `#model-list .model-row` selector occurrences** — `tests/browser/core.cjs:71,97,236,293`, `migration.cjs:128,131`, `orphan.cjs:135,137,143,147,179`, `stress.cjs:143`, `validation.cjs:195` — **plus 2 inner lookups in the same family** (`validation.cjs:198` `.model-row-name`, `:200` `.model-row-title`), i.e. **15 sites across five suites**. Selector-plus-text bindings are narrower than they look: `core.cjs:75,109` and `validation.cjs:104,153` click `#view-models button:has-text("Добавить")` / `("Add")`, which is `models.add` («Добавить» / "Add", `index.html:301`) — a value this design does **not** rename — and `i18n.cjs:214,221` read `#view-models h1` but compare it against `t('models.title')`, so they are **value-agnostic**: they pass whatever the title says and **no maintained test pins the section title literally**. `.model-row` is **shared** with the Pipelines list, which emits the same markup from `renderPipelines()` (`app.js:764`, `:790`) and is asserted through it at **26 `#pipeline-list .model-row` sites** in `pipeline.cjs` (`:189,318,319,348,371,379,412,419,438,439,443,523,524,567,568,621,658,660,663,689,693,800,806,810,822,928`, of which `:189,318-319,663,689` are the load-bearing ones). D9's class-family question is answered by **Q7** (separate classes; Pipelines untouched), so that 26-site block is a **byte-identical** regression surface rather than an open choice, and the cards slice stays gated on §Visual contract.

## Scope

**In scope:** the section's product vocabulary; a closed six-value category vocabulary with built-in icons; two optional fields on the existing service entity; catalog filtering; the service card markup; the ⓘ info card and its secrets-safe content rules; forward/backward compatibility of stored records and of the portable bundle; the launch-neutrality guarantee; the test and documentation obligations of the resulting slices.

**Non-goals (explicitly out of scope):**
- **User-defined categories, category CRUD, a category directory, a `categories` collection, category endpoints, category name rules, category delete policy, category management UI** — all of these are **deleted** by FD-1/FD-4, not deferred inside this design. A future request for them is a *new* ADR, not a slice of this one.
- **User-supplied category images** — FD-1 fixes the icon per category. The upload question that rev 1 raised (and Q6 closed) no longer arises, because nothing user-supplied is stored per category.
- **Pipelines** — R1–R5 speak about services. Under **Q7** the Pipelines list is a *regression surface* only, and an intentionally decoupled one: services move to their own card class family, so Pipelines keep `.model-row` (`app.js:790`) byte-unchanged and the 26 `#pipeline-list .model-row` selector sites must pass unmodified (§D9, §Test obligation 9).
- **Secret / credential storage** — R5 is a *display* rule. Model environment values stay stored exactly as today; ADR 006 remains the open direction.
- **GoAl Variables / path portability** — ADR 018 D8 keeps them deferred; nothing in this design needs a path.
- **Server-side filtering, pagination, search ranking** — the catalog is a local, fully loaded list; FD-3 asks for a filter control, not a query API.
- **Launch / lifecycle semantics** — R7 forbids influence, ADR 015 stays **FROZEN**, and nothing under `internal/process/` is touched.
- **Tags / multiple categories** — a service has zero or one category from the closed set.
- **The forward-version storage guard** — per FD-6 this is the standalone task `SCHEMA-VER-01`, and **Q22 ratifies that it does not block the catalog**: this ADR neither fixes it nor waits for it, and it runs whenever the Owner schedules it (see D5's honest consequence).
- **Transfer of the new fields to another install** — per FD-5 designed separately (D11).

### D3 — Category is a **closed vocabulary**, not an entity

Six stable tokens, defined once in the domain layer, each with one built-in icon and one label per locale. Proposed shape, following `instance.go:9-21`:

```
internal/domain/category.go
  type Category string
  const (
      CategoryModels  Category = "models"     // «Модели»    / "Models"
      CategoryImages  Category = "images"     // «Изображения» / "Images"
      CategoryAudio   Category = "audio"      // «Аудио»     / "Audio"
      CategoryVideo   Category = "video"      // «Видео»     / "Video"
      CategoryTools   Category = "tools"      // «Инструменты» / "Tools"
      CategoryOther   Category = "other"      // «Прочее»    / "Other"
  )
  var AllCategories = []Category{…}                 // the closed set, one source of truth
  func ValidCategory(s string) bool                 // "" (uncategorized) is accepted; anything else must be in the set
```

- **No `CategoryEntry` type, no `categories` collection, no repository interface change, no `/api/v1/categories`, no category service, no category management UI** (FD-1, FD-4). `docs/ARCHITECTURE.md:7`'s "simplified **4-entity** domain" statement therefore stays true.
- **Identity is the token, and the token is the label's key** — there is no ID/name pair to keep in sync and no rename question to decide; a display-name change is an i18n value edit with zero stored bytes.
- The JSON value is a **plain string** (`launch_instance_entry.go:19` is the precedent for a persisted field whose vocabulary is a typed set elsewhere), so decoding needs no custom unmarshaller.
- **The six tokens are the Owner's list, not this ADR's invention** (their names come from FD-1). **RATIFIED (Q18, Owner ruling 2026-10-03):** the stored ASCII values are exactly **`models, images, audio, video, tools, other`** — the spellings above are therefore the contract, not a proposal, and a future slice may not silently re-spell them (`model`, `media`, `misc`, capitalized or RU-transliterated variants are all out). Q18 also asked the Owner to choose knowingly that one category is **«Модели» inside a section renamed «Сервисы»**, while the technical entity stays `Model` (Q1) and identifiers stay `models.*` / `#view-models` (Q2); that collision **is now the Owner's ratified outcome**, so a reviewer must not read it as a leftover of the rename. Because the token doubles as the label key suffix (`models.category.<token>`, §D7) and as the filter `<option value>` (§D7), these six strings are load-bearing in three places at once — Go constant, i18n key, DOM value — which is why a rename of a *label* is a free i18n value edit but a rename of a *token* would strand every stored row that carries the old one — it degrades to uncategorized per D8, losing the user's organization silently while leaving the service intact.

### D4 — `ModelEntry` gains exactly two optional fields; the API gains no endpoint

```
ModelEntry + Category    string `json:"category,omitempty"`     // closed token; "" = uncategorized (FD-2)
           + Description string `json:"description,omitempty"`  // the user's own ⓘ text (R5)
```

- **`category`, not `category_id`.** There is no entity to reference; an `_id` suffix would imply a foreign key, resurrect the dangling-reference problem rev 1 needed D8 for, and make a stored value meaningless without a join. The field stores the vocabulary member itself.
- **Create:** the body decodes straight into the persisted struct (`handlers/models.go:111-113`), so the new fields arrive unvalidated; **`ModelService.CreateModel` (`model_service.go:41-46`) validates the token** exactly where it validates the name today. **Patch:** `ModelPatch` (`repository.go:911-918`) gains `Category *string` and `Description *string`; `PatchModel` (`:920-949`) gains one `if p.X != nil` branch per field, inside the existing `saveLocked()` + rollback discipline. `nil` preserves, `""` clears — the same `*string` semantics `Name` already has, except that empty is a *legal* value for these two (`Name` rejects it at `model_service.go:53-55`).
- **Responses:** `modelResponse` (`:19-29`) and `newModelResponse` (`:31-47`) gain both fields — neither is secret, and `:31-47` remains the only place that decides what leaves the process, keeping the env **keys-only** rule intact.
- **Update handler:** the pointer struct at `:136-143` gains two fields and the patch build at `:159-166` passes them; the audit list at `:178-196` gains `changed["category"]` / `changed["description"]` (names only, never values — `:176-177`, `docs/API.md:105`).
- **Zero new endpoints and one new validation helper** — `POST/PUT /api/v1/models*` already carry a full/partial `ModelEntry`. `ValidCategory` is the only new function on the write path, and its error message follows the existing closed-set diagnostic shape (`loglevel.go:22`): `category must be one of models, images, audio, video, tools, other (got "…")`, surfaced as `400 bad_request` by the handler's existing `apierrors` branch (`handlers/models.go:167-175`).
- **`domain.Model` does not gain either field** (see D12). `ModelEntryToDomain` (`model_entry.go:75-87`) is therefore **not** touched — a deliberate omission, not an oversight.
- **Description bound — RATIFIED (Q20, Owner ruling 2026-10-03):** the category select and the description field live **in the service form** (the existing add/edit wizard — Create and Edit are the same modal, `index.html:139-210`), and **description is at most 2000 characters**, enforced server-side in the **same service-layer call** that validates the token (`model_service.go:41-46` / `:52-60`), because that is the single boundary both write paths pass through and a UI counter is not a contract. Three consequences are recorded rather than glossed:
  - **"characters" means Unicode code points**, so the check is `utf8.RuneCountInString(p.Description) > 2000 ⇒ reject`, **not** `len(string) > 2000` — a Russian description is 2 bytes per letter, and a byte check would halve the user's allowance for exactly the locale this project targets. `grep -rn "RuneCountInString" --include=*.go internal/` returns **0 today**: this is the project's **first length bound on free-text user input** (`Name` is bounded only by emptiness at `model_service.go:53-55`). The nearest existing shape is the hostname rule in `internal/webui/validation/port.go:37`/`:45` ("must be at most 253 characters" / "1-63 characters"), which is a **handler-side** check on a config value — D4 deliberately does **not** follow it here, because `handlers/models.go:111-113` decodes the create body straight into the persisted struct, so a handler-side rule would be bypassable by any future caller of the service.
  - **The rejection is a `400`, the same posture as an unknown token**, with a bounded message naming the limit and the received count and **never echoing the text** (mirroring `handlers/models.go:176-177`, which logs field names and not values). Truncating silently is rejected: it would let the user believe a description survived.
  - **Which wizard step** holds the two inputs was **not** part of the Owner's ruling — Q20 asked placement and bound together, and the ruling settles placement at the level of "the service form" and the bound at 2000. The design's proposal remains **Step 1 «Название»** (`index.html:145-150`, currently exactly one field), on the ground that organization belongs with the name rather than with launch parameters (Step 3 is autostart + env + args, `:190-210`); Step 3 is not touched. Because that last item is a layout detail inside an already-agreed surface, it is **not** an open question about the design; it is named in §Explicitly NOT decided and must appear in slice B's contract before any markup is written.

### D5 — **No schema version bump: v8 stays current**

`SchemaVersion()` keeps returning `8` (`repository.go:552`) and `writeUnified` keeps writing `8` (`:530`). No migration function, no load-branch change, no normalization, no test-corpus retarget.

**Why — the precedent is this repository's own, and it was ratified:** ADR 013 §D6 states "**No schema version bump** (stays v8)" with the proof that `load()` has one version-agnostic `else` branch above 6, `encoding/json` ignores unknown keys, and missing keys decode to zero values (`013-…md:101`), and the Owner agreed it as decision item (5) conditional on test-proven backward compatibility (`:214`). The git record matches the claim: `3347b2b` added persisted fields (`pipeline_entry_id`, entry `id`, `EnvPatchOp`) **without touching the schema literal** and *added a test that asserts no bump happened* (`pipeline_test.go:523` — `"schema_version = %d, want 8 (no bump)"`). No commit since `9f0ecf5` introduced the literal has changed it.

FD-4 asked this design to reconsider the need for v9. **It is not needed**, because the two reasons rev 1 gave for bumping are both gone: there is no new collection to normalize, and no new required invariant for a legacy file to violate — a v8 file with no `category` / `description` is *already* a valid catalog state (every service uncategorized, every description empty), which is precisely the backward-compatibility requirement R6 asks for.

What no-bump avoids, stated as the measured cost it prevents: **seven literal `8` assertions in six test functions across five files** (§Evidence row above; the seventh is `cmd/goal/autostart_test.go:283`, outside `internal/storage/`) retargeted — and "re-target, never delete" would have been the rule; `tests/browser/migration.cjs`'s v5→current fixture chain re-verified (`:17` seeds `schema_version: 5`, `:94` asserts the result is `8`); and **eleven statements in six documents** (`LIMITATIONS.md:70` and `:105`, `CONFIGURATION.md:259`, `ARCHITECTURE.md:5` and `:12`, `ARCHITECTURE_RU.md:5` and `:12`, `USER_GUIDE.md:1064` and `:1066`, `USER_GUIDE_RU.md:1031` and `:1033`) that currently read "v8 is current" would otherwise go stale in the same slice. Under D5 they all stay correct **unedited**, and `ARCHITECTURE.md:7`'s "4-entity domain" stays true because no fifth entity arrives. Excluded from that count on purpose: the ADR-history table rows (`ARCHITECTURE.md:163`/`:165`, `ARCHITECTURE_RU.md:159`/`:161`), which are dated records of what each ADR shipped and are not falsified by a later bump.

**RATIFIED (Q3, Owner ruling 2026-10-03): schema stays v8, at confirmed compatibility.** The Owner accepted no-bump on the same condition ADR 013 attached to its own §D6 (`013-…md:214`, item (5): "conditional on test-proven backward compatibility"), and this record binds that condition to a named artifact rather than leaving it as a mood: **§Test obligation 1 is the proof, and it is a gate, not a nicety** — if a v8 file without the two keys fails to load, or a categorized+described service fails to round-trip, or any of the seven literal `8` assertions needs moving, the compatibility the ruling was conditioned on is **not** confirmed and D5 returns to the Owner instead of being quietly overridden in code. A bump buys nothing here anyway: an older binary ignores `9` exactly as it ignores unknown keys today, because nothing checks the version (`repository.go:254-272`).

**The honest consequence, which this record does not smooth over:** with no bump the durable file carries **no signal whatsoever** that it contains catalog fields. An older binary will read `category` / `description` into nothing and rewrite the file without them — silently, with no version marker even to warn about. That is not a new class of risk introduced here (it is exactly what `3347b2b` already did to `pipeline_entry_id`), and a version guard would not have caught it either, because the hazard is *unknown fields*, not a *higher number*. The related guard problem — a file whose `schema_version` exceeds the binary's own — is therefore kept as the **standalone task `SCHEMA-VER-01`** per FD-6, with two options it must decide (fail-closed guard mirroring `portable.go:130-132`, or documented acceptance of the downgrade plus a WARN). **RATIFIED (Q22, Owner ruling 2026-10-03): `SCHEMA-VER-01` does not block the catalog.** The guard is scheduled on its own merits, before or after ADR 020, and no catalog slice may absorb it or wait on it. This is the correct ordering rather than a convenience: the guard's own subject (a *higher version number*) is not what the catalog changes, so gating the catalog on it would couple two unrelated decisions and would still leave the unknown-*field* case uncovered (`SCHEMA-VER-02`).

### D6 — Icons are built-in **per category**; nothing is stored per category

Each of the six tokens maps to one inline-SVG constant, and an uncategorized service renders a default. This is FD-1's second sentence ("each category has a built-in icon") applied to the substrate that already exists: `ICONS` (`app.js:425-434`) is an 8-entry inline-SVG map interpolated as trusted markup by `iconBtn` (`:421-423`), so a six-entry `CATEGORY_ICONS` map is the same mechanism, not a new subsystem.

- **No stored image field at all.** Rev 1's `image` field, its `"<family>:<name>"` token grammar, and its I-A…I-D option table are **deleted**: the icon is a function of the category, and the category is a closed token, so nothing per-category is persisted. Q6's built-in-glyph ruling is thereby *subsumed* — FD-1 removed even the user's choice of glyph.
- **The security property strengthens, it does not weaken.** The value that reaches the renderer has been validated against a six-member set, so no stored string can become markup; `esc` (`:394`) and `safeId` (`:413`) remain the only user-text interpolation helpers; and the no-upload invariant stays true by construction (zero `multipart` / `FormFile` handlers in `internal/`), which §Test obligations asserts rather than assumes.
- **RATIFIED (Q21, Owner ruling 2026-10-03): built-in SVG icons, drawn in the project's existing style.** Concretely: a closed `CATEGORY_ICONS` map beside `ICONS` (`app.js:425-434`), six entries keyed by the six tokens plus one neutral default, each entry the same shape as today's eight — an inline `<svg viewBox="0 0 24 24">` with path data interpolated as trusted markup — so the icons ship inside the already-embedded `static` set (`server.go:36`) and add no request, no font, no external asset and no `Content-Security-Policy` question (the package has none today, which is precisely why the existing markup renders). "In the existing style" is the binding constraint on the artwork, and the style is measurable rather than a vibe: `viewBox="0 0 24 24"`, filled path data, and a single color inherited through `fill: currentColor` (`.icon-btn svg` at `style.css:258`, `.pl-act svg` at `:508`, both sized by CSS at 20–23 px rather than by the markup) — so a category icon is a monochrome silhouette that takes whatever color its container has, and no multi-color illustration or per-state recoloring enters the design. The uncategorized / invalid-token default is one entry in the same map, not a hidden state elsewhere (D8).
- **Where an icon may not appear is settled by the platform, not by taste: not inside the category `<select>`.** D7's filter is a native `<select>` with eight literal `<option>`s, and HTML `<option>` elements render **text only** — an `<svg>` child is not displayed by the browsers this project supports, so an "icon in the filter option" design would silently ship six invisible icons. The icon therefore lives on the **card** (its own slot, sized by §Visual contract) and, if the Owner's contract asks for it, in the **ⓘ header**; the filter stays text-labelled. This is the one point where FD-1's "each category has a built-in icon" had to meet a byte-level constraint, and the constraint wins.
- **The card slot's exact size, position and overflow behavior remain the visual contract's**, not this ADR's (§Visual contract): Q21 settles *what* the icons are and *how* they are drawn; Q7's artifact settles *where* they sit on the compact card, and slice C is gated on that artifact.

### D7 — Filtering: one static closed `<select>`, client-side, AND-composed

Add `<select id="mf-category" onchange="renderModels()">` inside `#models-filter-bar` (`index.html:303-315`) with **eight literal `<option>`s** — «Все» (`value=""`, default), the six categories (`value="models"`, …), and «Без категории» (`value="none"`) — each labelled by `data-i18n`, exactly as `#mf-state` is written today (`:307-315`). `renderModels()` gains one predicate beside `:527-533`, combined by **AND** with search / runtime / state / autostart; the existing no-match empty state (`models.filter.no_match`, `ru.json:43`) is reused unchanged.

- **No population code and no new endpoint**: the options are markup, so unlike `#mf-runtime` (`:306`, filled at `app.js:302`) nothing reads a category list at runtime. A useful side effect is coverage — `data-i18n` attributes **are** collected by `TestI18nDictionariesParity` (`server_test.go:69`), while a JS-composed label key would not be (that test's `tCallRe` at `:73` matches only a `t('…')` call that closes immediately after the literal). Choosing static options therefore puts the six new labels under the existing parity gate for free.
- **Label keys live under `models.category.*`, not a new top-level `category.*` group** — the flat-prefix convention D2 keeps (`models.filter.*` at `ru.json:38-43`, `models.status.*` at `:53-60`), and the reason is a coverage coupling rather than tidiness: the runtime raw-key detector's regex (`tests/browser/i18n.cjs:167`) allowlists top-level prefixes explicitly, so `models.category.audio` is caught if it ever leaks as text while a key under an unlisted new group `category.*` would pass unnoticed until that regex is extended. ### D8 — An invalid stored token degrades to *uncategorized*; nothing blocks startup

A hand-edited file may contain `category: "gpu"`. Rule: **validate on write, degrade on read.** The service layer rejects an unknown token on create/patch (D4); at render time an unrecognized value is treated as uncategorized by both the card and the filter (`none` matches it, per D7), startup never fails, and the stored value is not rewritten behind the user's back.

The precedent for degradation-not-repair is `getRuntimeName` (`app.js:317-320`): an unknown runtime id shows the raw id, an empty one shows `'—'`; nothing refuses to render and nothing edits the file. Rev 1's "one bounded `WARN` at load" is **not** adopted by default (it would add a per-entry log line to the load path for a case that display already handles; `slog.Warn` is available in-package if the Owner wants it — `config_seed.go:30`). Rev 1's stale-`category_id` question no longer exists: there is no reference to become stale, and `ValidateCrossReferences` (`repository.go:1321-1337`, **zero production callers**) is not extended — the closed set needs validation, not a cross-reference check. That validator's unwired state stays where it belongs: BACKLOG **`CATALOG-DEP-02`**, as debt independent of this ADR. **RATIFIED (Q19, Owner ruling 2026-10-03): an unknown category is *displayed* as «Без категории» and the stored data is not changed.** That is exactly this rule, and it closes both halves of what Q19 asked: **degrade on read** is adopted, **normalize-to-empty on load** is rejected — a load path that rewrote the user's file would destroy the very value that made the row uncategorized, would do it without the user asking, and would have no repair precedent to stand on (`getRuntimeName` degrades; nothing in the repository repairs references on read, and ADR 013's backfill at `013-…md:102` covers *generated entry ids*, not values a human typed). Two consequences are stated so the slice does not discover them: the unknown token remains in the file and will reappear in the API response as what it is (`modelResponse` echoes `category` verbatim), so **the browser suite asserts the DOM shows «Без категории» while the file still holds `"gpu"`** — the pair is the test, not either half alone; and if the user later edits that service and picks a real category, the explicit write replaces the bad token through the normal patch path, which is the only way stored data ever changes. No `WARN` is added at load (rev 1's option, still not adopted; `slog.Warn` remains available in-package at `config_seed.go:30` should the Owner ever want one).

### D12 — Categories are launch-inert (R7), proven by omission

`category` and `description` are persisted on `ModelEntry` and returned in `modelResponse`. They are **absent from `domain.Model`** (`model.go:20-30`) and from `ModelEntryToDomain` (`model_entry.go:75-87`), which is the single hand-written bridge from persistence to the launch domain and the only shape the launch path can read (callers `instance_service.go:40`, `:94`; `pipeline_service.go:455`; `handlers/models.go:383`). The launch surface is further bounded by signature: `LaunchResolver.Resolve` / `.Validate` (`internal/domain/command.go:53`, `:167`) consume `Runtime` + `Model.Args` + `Model.Environment` and emit `domain.CommandSpec` (`:14`); `Supervisor.ResolvePreview` (`internal/process/supervisor.go:547`) and `Supervisor.AdmitAndStart` (`:602`) take a `Model`, a `Runtime`, and explicit custom args/env — no parameter into which a catalog field could be passed; the persisted launch snapshot is the same four fields (`launch_instance_entry.go:15-18`).

So R7 holds **structurally and by omission**: to reach a launch, a category would have to be *added* to the launch-domain struct first, which is a separate change with its own ADR. FD-1 makes this stronger than rev 1's version — with a closed set, no category can carry a path, a URL, a markup string or a per-category image at all, so there is nothing for the launch path to misread. Asserted, not assumed, by §Test obligations 5 — the same "prove reachability" discipline the repository applies to `PipelineModel.AutoStart`, whose inertness had to be re-documented (ROADMAP P1, ADR 013 correction).

## Test obligations (for the implementation slices — none of these exist today)

Rev 1 listed fourteen obligations; FD-4 asked for simplification. These ten cover the design, and each is stated so a suite can reproduce it:

1. **Backward compatibility without a bump (R6) — this is Q3's stated condition, so it is a gate and not a nicety:** a repository file with **no** `category` / `description` keys loads unchanged, every service appears and is uncategorized with an empty description; a categorized+described service round-trips through save/reload with both fields intact; and `SchemaVersion()` **still returns `8`** — mirroring the existing "want 8 (no bump)" posture at `pipeline_test.go:523`. The seven literal `8` assertions in six test functions across five files (§Evidence row above; one of them is `cmd/goal/autostart_test.go:283`) are asserted **byte-unchanged**, not retargeted. **If any half of this fails, the compatibility Q3 was conditioned on is not confirmed and D5 returns to the Owner** rather than being settled by adding a bump inside an implementation slice.
2. **Closed-set validation (D3/Q18) and the description bound (D4/Q20):** each of the six tokens `models|images|audio|video|tools|other` is accepted; `""` is accepted and means uncategorized; an unknown token is **rejected with `400` on both create and patch**, with a bounded message naming the got value; **`description` of exactly 2000 code points is accepted and 2001 is rejected with `400`**, and the boundary is proven with a **non-ASCII** string — a 2000-letter Russian description must be **accepted** and a 2001-letter one rejected, because a `len(string)` byte check would reject the 2000-letter case at ~4000 bytes and so would silently halve the allowance for exactly the locale this project targets); an **absent or null** patch field preserves the stored value while an explicit `""` clears it; the rejection message **never echoes the description text**; and the storage layer demonstrably performs no validation (both rules live in the service, like `Name`).
3. **Invalid stored value (D8, per ratified Q19):** a hand-edited `category: "gpu"` loads without error, **renders as «Без категории»**, is matched by the «Без категории» filter option, and the **file bytes are re-read after the load and still contain `"gpu"`** — the pair (DOM degraded + file unchanged) is the assertion, since either half alone would also pass under the normalize-on-load posture the Owner rejected. No `WARN` is required by this design, so none is asserted. The next **explicit** patch of that service may set or clear the value through the normal write path, and that is the only way it changes.
4. **Filtering (R3):** Все / each of the six / Без категории, each AND-composed with search + runtime + state + autostart; `none` matches both empty and invalid values; the no-match state still renders; the eight `<option>` values and the Go `AllCategories` set never diverge (an enumerated parity check over `data-i18n` keys in both dictionaries — the composed-key blind spot in `server_test.go:73` means parity is *not* automatic for JS-built labels).
5. **Launch neutrality (R7):** a categorized, described service produces a **byte-identical** `CommandSpec` to the same service uncategorized (assert at `LaunchResolver`/`ResolvePreview`), and `domain.Model` / `ModelEntryToDomain` demonstrably carry **neither** field — the omission is the proof, so assert it at the struct/bridge level, not only by behavior.
6. **Secrets safety (R5):** the ⓘ card's data path returns `environment_keys` only; a model whose env values contain a sentinel string never shows that value in the resolve response, the list response, or the rendered card DOM.
7. **ⓘ interaction (R5):** hover opens; click opens with no hover (keyboard-reachable); one card open at a time; ESC/outside-click closes; resolve is requested **once** per opened card and cached (assert request count, proving D10's no-fan-out rule); a 400 variable diagnostic renders instead of a generic failure.
8. **Portable, unchanged (R6, per ratified Q9 + FD-5, read against Q11):** export from a categorized install produces a **valid bundle v1 with an unchanged shape** carrying **no** `category` / `description` keys; importing it into a clean install creates services **with no category and no description** (the documented loss); importing it over an install whose **same-id** service *does* have them **leaves the local `category` and `description` in place** (D11's NEW-vs-UPDATE distinction, which rests on ADR 018 §D7/§D11 restoring field-by-field — `018-…md:112`, `:147`); **zero bytes changed** under `internal/application/portable/`, `internal/storage/import_plan.go`, `internal/webui/handlers/portable.go` and `tests/browser/portable.cjs` — the negative assertion is what proves the ruling was honored. TLS material and env values stay out of the bundle (ADR 019 §D25 / obligation 12 at `019-…md:330`; ADR 014 D13) — re-asserted, not inherited. **Sequencing note this obligation carries:** the UPDATE half is only executable once ADR 018's apply path exists, which Q11 guarantees; until then the same-id case cannot be produced at all, because skip-existing classifies it `existing` and never touches it (`import_plan.go:144-218` per ROADMAP `:152`).
9. **Card redesign (R4, per ratified Q7 + Q8):** markup asserted against the **committed visual contract's numbered V- items** (§Visual contract) — never phrased as "matches the mockup"; the **15** service-side browser sites (§Blast surface) retarget to the new family and pass; RU/EN parity (`tests/browser/i18n.cjs`); **and all 26 `#pipeline-list .model-row` selector sites in `pipeline.cjs` pass unmodified** — under Q7 that file is *evidence of non-coupling*, not a file to edit, and any need to touch it means the ruling was violated. The **Q8 fix is asserted in the same slice**: after it, no element in `#model-list` carries a native `title` attribute (query the rendered DOM, both locales, with a categorized service and an orphan one so `:564` and `:565` are both reached), that each of those two elements now carries `data-tooltip` with the same text it dropped from `title` (the swap must not lose the information), and that `app.js:795`'s pipeline `title=` is still present and untouched.
10. **No new attack surface (D6/Q21):** the icon map contains exactly the six tokens plus a default, and each value is inline `<svg>` markup of the same shape as the existing `ICONS` entries — **no** user string reaches it; **no user text reaches the description rendering unescaped** (`esc`, `app.js:394`) — the 2000-character bound is a UX/data-hygiene rule, **not** the XSS control, and the test must exercise a description containing `<img src=x onerror=…>` to prove the escape is what protects the page; and the suite asserts the *absence* of any upload surface stays true (no `multipart` / `FormFile` handler appears in `internal/`), so a later extension cannot smuggle one in under this slice.

(Items 1–10; the four that disappeared with the CRUD design were category CRUD persistence, the name-uniqueness rule, the dangling-`category_id` repair, and the image-token rejection — none of those objects exists in this design, so no test may pretend to cover them. ## Consequences

- The catalog arrives as **a vocabulary plus two optional fields**, not as an entity: no fourth collection, no new endpoint, no migration, no version bump, and `ARCHITECTURE.md:7`'s "4-entity domain" stays accurate. FD-1 traded the user's freedom to invent categories for a design that touches a small fraction of the surface — that trade is the Owner's and it is now recorded as decided, not as this ADR's preference.
- **The organization is code, so it cannot rot.** A closed set cannot be deleted from under a service, cannot have two members with confusingly similar names, cannot be referenced danglingly, and cannot be smuggled into a bundle or a launch. Rev 1 needed D5's delete-conflict rule, D8's dangling-reference rule and Q4's uniqueness question precisely because it stored user-created rows; all three are gone.
- **What the user loses is real and should be said plainly:** they cannot invent a category. Six fixed buckets will misfile some services (a TTS server is Аудио or Инструменты or Прочее, and only the Owner's set decides), and «Прочее» will absorb the residue. That is the accepted cost of FD-1, not a defect to fix later in a slice.
- **R6's portable half is a documented loss, not a silent one** (D11). A migrated install keeps its services and loses their category and description; because FD-5 chose separate transfer design rather than a bundle change, that statement belongs in `API.md`, both user guides and a new `LIMITATIONS.md` section.
- **The sharpest consequence moved out of this ADR.** Under D5 the durable file records no signal that catalog fields exist, so an older binary discards them on the next save exactly as it already discards `pipeline_entry_id` — and a `schema_version` upper-bound guard would not have caught that case, because the case is unknown *fields*, not a higher *number*. The guard problem the rev-1 design uncovered stays registered on its own merits as `SCHEMA-VER-01` (FD-6), and this record does not claim it is solved, scheduled, or unnecessary. Its sibling is registered beside it as **`SCHEMA-VER-02`** — the fact that unknown-*field* loss already occurs between binaries that share the literal `8` (`3347b2b`, ratified as ADR 013 §D6 and pinned by `pipeline_test.go:523`) — so `SCHEMA-VER-01`'s fail-closed option is never later sold as a complete fix.
- **The secrets rule (R5) is already satisfied by the existing resolve contract**, so the ⓘ card adds no exposure *if* it consumes `environment_keys`; that is why D10 pins it to the existing endpoint instead of inventing a payload.
- **The shared-mechanism risk is now split in two, and only one half remains.** Q7 gives services their own card family, so the `.model-row` coupling with Pipelines (`CATALOG-DEP-04`) stops being a live hazard for catalog work and becomes a documented reason the pipeline files must not move; the *tooltip* coupling does not go away — the ⓘ card is required to live inside the canonical `#goaltip` system, and Q8's ruling removes the card's two existing violations while `app.js:795` keeps the pipeline one. So the residual risk in slice C is regression in a suite the slice is forbidden to edit, which is why obligation 9 names the 26 selector sites as evidence rather than as a tripwire.
- **Vocabulary is a product-surface decision, and it is now the Owner's made one.** Q17 renames the section **and its form**, so after the change the nav says «Сервисы», the wizard says «Добавить сервис» / «Название сервиса», while the **Pipeline** entry editor still says «Добавить модель» (`ru.json:82`, `pipelines.btn.add_model`), a runtime-deletion prompt still counts "модели" (`runtimes.delete.cascade`, `runtimes.delete.dependents`), and the history/instances tables keep a «Модель» column (`history.col.model`, `instances.col.model`). Inside the section, Q18 keeps a category called **«Модели»** living under a heading called «Сервисы». None of that is an oversight to correct in a slice: it is the boundary the Owner drew between user-facing section vocabulary and technical terminology (Q1), and a future reviewer who "harmonizes" the remaining strings would be overruling Q17 without a decision.
- **What this design found pre-existing, and what it did not cause** — every one of these is a repository fact that stands whether or not the catalog ships, and each is registered in [BACKLOG.md](../../BACKLOG.md): **CATALOG-DEP-01** (no committed home for an Owner-accepted visual contract — the blocker this ADR's §Visual contract proposes a mechanism for, and the one rev-3 ruling that did **not** dissolve: Q7 re-affirmed the artifact as mandatory), **CATALOG-DEP-02** (`ValidateCrossReferences` has zero production callers; §D8 leaves it alone), **CATALOG-DEP-03** (the card's two native-`title` violations — **now scheduled away**: Q8 rules they are fixed in the catalog's UI slice, so the debt's required direction has an owner and a slice, while `app.js:795` and the two empty `title=""` selects stay out of its scope), **CATALOG-DEP-04** (`.model-row` as one family serving two views — **resolved for services by Q7**, and it remains true for anything that later reuses the pattern, since Pipelines keep the class), and **CATALOG-DEP-06** (the raw-key detector at `tests/browser/i18n.cjs:167` allowlists top-level prefixes and `server_test.go:73` sees only literal `t('key')` calls, so a **new** i18n group could ship untranslated and pass both gates — which is a reason §D7 places the labels under `models.category.*` rather than a cosmetic choice, and it is unaffected by any of rev 3's rulings). **CATALOG-DEP-05** was promoted out to `SCHEMA-VER-01`/`-02` per FD-6 and leaves only a dated pointer.
- **Q11 buys the design an ordered world and costs it freshness.** Because nothing here may be built until ADR 018 is finished and OWNER-IMPORT-01 is closed, the catalog will be implemented against a repository whose import behavior is *already* the NEW/UPDATE/UNCHANGED/BLOCKED one — which is why D11's UPDATE-preservation is stated as a reliance instead of a request, and why §Sequencing item 0 obligates a re-read of this record's `import_plan.go` / `repository.go` / `portable.go` citations before slice A is contracted. Every line number in this record was measured at HEAD `c4241e2` on 2026-10-03; by the time the gate opens, some will have moved, and a moved citation is corrected in this file first, never argued from memory.
- Nothing here closes any open acceptance case: **OWNER-IMPORT-01**, OWNER-UX-01's formal closure and Manual Owner Acceptance remain **OPEN** (ROADMAP `:152-155`, `:164` — `:152-154` and `:163` in this record's 2026-10-03 numbering, before ADR 018's Slice 1 commit added a line to that block), ADR 015 remains **FROZEN**, and ADR 018's **Slice 1** is now IMPLEMENTED, COMMITTED and PUBLISHED (`85c7e9ca699f61668f5f441926ed09cda37bd1bd`, exact-SHA CI run `37185521486`, attempt 1, all 7 required jobs PASS) while its remaining slices stay **NOT STARTED**, so the gate Q11 imposes is still closed; nothing in this record ever edited ADR 018's bytes. **OWNER-EXPORT-01 is CLOSED** — OWNER PASS on the Owner's own `https://aids:8443` re-acceptance, recorded 2026-10-03 at ROADMAP `:162` — and this ADR neither reopens nor depends on it; ADR 019 §D27's secure-origin path is cited only as the reason a file-choosing export already exists. Under **Q11** the first three stop being merely unrelated open items and become the catalog's own start gate.

## Visual contract — how the Owner's out-of-repo mockup becomes canonical (mechanism for Q7)

R4 references «согласованный визуальный макет». On 2026-10-03 the Owner confirmed it **exists outside the repository** and asked for a mechanism to bring it in. The repository evidence is unchanged: `docs/` holds **zero** non-`.md` files (`find docs -type f ! -name "*.md"` → empty); `docs/tasks/` (3 files) and `docs/acceptance/` (3 files) are markdown-only; nothing matches `*mockup*`, `*wireframe*` or `*.canvas.tsx`; the only bitmaps are `winres/icon.png` / `winres/icon16.png` (application icon) and third-party `node_modules/` assets. AGENTS.md §Source of Truth requires an accepted *direction* to live in the canonical files, not only in chat — an accepted **visual** contract is the same class of thing.

**Rev 3 status of this section: the mechanism is still the plan, and the artifact is still missing.** Q7's ruling settled the half this record could settle — services get their own card classes and Pipelines are not touched (§D9) — and re-affirmed the other half verbatim: «Визуальный макет остается обязательным перед UI-реализацией». Nothing was delivered into `docs/assets/adr020/` by the ruling, and this ADR does not invent the layout in its absence, so R4's acceptance target remains unavailable to every reviewer until the Owner supplies it by one of the three paths below.

**V-A (proposed) — commit two things, and bind acceptance to the second:**

1. **A pixel reference, committed as an asset:** `docs/assets/adr020/services-catalog-cards.png` (the directory does not exist yet — it would be the first non-markdown home under `docs/`). Committing a binary is demonstrably safe rather than assumed safe: tracked binaries already exist (`winres/icon.png`, `winres/icon16.png`), there is **no `.gitattributes`**, and `core.autocrlf=true` does not rewrite binary content, so a PNG introduces no line-ending hazard. Each asset gets provenance lines in the spec that references it: date received, «provided by the Owner on 2026-10-03, committed unmodified», and its `sha256` — so a later edit is detectable instead of arguable.
2. **The canonical contract itself: `docs/acceptance/ADR020-SERVICES-CATALOG-VISUAL-CONTRACT.md`**, following that directory's naming convention (`ADR011-WINDOWS-SERVICE-MANUAL-ACCEPTANCE.md`, `ADR019-HTTPS-BROWSER-ACCEPTANCE.md`). The image is *evidence*; this file is what slices are accepted against. It must state, in testable terms: card anatomy (which field on which line — name, runtime, category icon, status, PID/uptime, action strip, ⓘ badge), geometry (grid/columns, min/max widths, behavior at 430px and at 150% zoom), the states (default / hover / ⓘ pinned / filtered-empty / **uncategorized** / description absent), RU vs EN overflow for long names and for the longest label «Изображения», and the icon slot's size and its default rendering when `category` is empty or invalid. Each item gets a numbered assertion **V-1…V-n** that the browser suite reproduces.

**How the Owner can supply the artifact — any one of these closes Q7's first half:**
- **(a)** attach or paste the mockup; the agent writes it to `docs/assets/adr020/`, records its `sha256`, and drafts the spec **strictly as a transcription**.
- **(b)** the Owner places the file at that path personally; the agent only references it and verifies the hash — no content authored by the agent at all.
- **(c)** if no file can be committed, the Owner dictates the measurements and states and the spec is committed as *«transcribed from the Owner's external mockup, Owner-confirmed 2026-10-03»*, with the external mockup labeled **non-authoritative** and the written spec named canonical.

**Two rules this mechanism exists to enforce.** No card acceptance may claim *"matches the mockup"* — it claims **V-k assertions pass**, because a claim about an image nobody can open is unverifiable. And the agent must not invent the contract: layout values are the Owner's product decision, so the file is written *from* the Owner's artifact or *from* dictated values.

**V-B (rejected):** keep the mockup external and record only a pointer. That reproduces the gap being closed, leaves R4 unauditable, and lets slice C be accepted on evidence no reviewer can read.

**Already registered:** the missing home for an accepted visual contract is **CATALOG-DEP-01** in [BACKLOG.md](../../BACKLOG.md) — deliberately wider than this ADR, since any future styling-dependent acceptance hits the same gap.
