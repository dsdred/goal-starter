## Context

### The finding

`InstanceController.Stop` is synchronous and stays synchronous: `POST /api/v1/instances/{id}/stop` returns `200 {"status":"stopped"}` only after the process has been stopped (`internal/webui/handlers/instances.go:119-132`), and `POST /api/v1/models/{id}/stop` behaves the same way (`internal/webui/handlers/models.go:258-280`). The consequence, established byte-by-byte in §Current-state forensic, is that the interval during which the instance is `stopping` **and the process is still alive** is exactly the interval during which the controller's read lock is held for writing. Any status read that arrives in that interval does not return stale data — it **blocks**. So a client cannot see "stopping while alive" at all; the first readable `stopping` is emitted after the process has already exited, and by then the terminal write from `wait()` is usually committed too.

This is an observability defect, not a correctness defect: no duplicate process is launched, no slot leaks, no ownership rule is broken, and ADR 016's durable contract holds throughout. What is missing is the ability of an operator — the Owner in a browser, or any API consumer — to see that a stop was accepted and is in progress.

### Label collision (recorded so the two never get conflated)

`ROADMAP.md:142` carries an **unrelated** finding also labelled **F-7**: ADR 019 Slice 5's pre-commit review finding about the new HTTPS suite's Linux-CI reproducibility, which that record closed as observed fact on 2026-10-01. The lifecycle finding is referred to in this ADR and in its acceptance document as **MA-06 F-7**, never as bare `F-7`.

### What shipped behavior already guarantees

Three properties are load-bearing here and this ADR does not touch them:

1. **One stop owner.** `wait()` is the single goroutine that owns `cmd.Wait()` (`internal/process/manager.go:343-345`), and ADR 016's residual-ownership contract (outcomes C/D, `internal/process/supervisor.go:1515-1536`) keeps slot and run ownership with it until exit is confirmed.
2. **Terminal authority in memory.** The terminal entry is captured under `ic.mu` and is not re-derived after a persist failure (`internal/process/supervisor.go:1819-1833`, ADR 016 T3).
3. **Arbitration is a single non-bypassable boundary.** Every production launch reaches `Supervisor.arbitrate` (`internal/process/arbitration.go:154-178`) and the restart state table is shared with the model-level preflight (`checkRestartTarget`, `internal/process/arbitration.go:304-320`), which allows `stopping` "without becoming a second stop owner".

### Why live `stopping` cannot be reliably observed

The claim is structural, not statistical. Steps 6→9 hold `ic.mu` for the entire lifetime of the live `stopping` state, because the lock is acquired before `Manager.Stop` is called and `Manager.Stop` does not return until the process is gone. Step 4 is therefore the *only* readable instant, and it is three statements wide (`:1560` → `:1562` → `:1580`). Two further facts close it:

- **A queued writer blocks later readers.** Go's `sync.RWMutex` does not let a new `RLock` pass a writer that is already waiting, so a reader that arrives during step 5 — while the state is `stopping` and the process is alive and the lock is nominally free — is queued behind the `Lock()` at `:1580` and is served only at step 9, i.e. after the process died.
- **The 3 s UI refresh cannot win the race.** `internal/webui/static/app.js:2360-2364` polls `reloadAllData` on a 3000 ms interval, and `isActive`/`modelStatus` (`app.js:335`, `:337-343`, rendering branch `:556`) already know how to display `stopping`. The client renders the badge only if a response arrives; the response is withheld by the server for the whole live interval, so the badge is a **post-mortem** indicator. The observed user-visible effect is `running` → (frozen or straight jump) → `exited`/`failed`.

`manager.go:222` does set the *Manager's* own `status.State = StateStopping` under `m.mu` and releases at `:224`, so `Manager.Status()` (`:307-311`) is technically readable during the wait — but no reader on the instance path consults it while a stop is in flight: `wait()` calls it only after `<-done` (`supervisor.go:1772`), and nothing else reaches through `ic.manager` to render state.

### The amplification: one stopping controller can stall decisions for every other model

`scanConflicts` holds `s.mu.RLock` for the whole registry walk (`arbitration.go:189-215`) and calls `ctrl.Snapshot()` at `:197` for **every** registered controller of **every** model, plus `ctrl.activeOperation()` at `:201`. Therefore, while any one instance is inside steps 6→9:

- a launch arbitration for a *different* model blocks in `scanConflicts` behind that controller's write lock;
- `Supervisor.Status`/`List`/`ListActive` (`supervisor.go:778-817`), `PreflightRestart` (`arbitration.go:327-347`) and `s.restart`'s pre-arbitration `ctrl.Snapshot()` (`supervisor.go:763`) block;
- and because a blocked `RLock` reader also prevents the *registry's own* writers, the stall is not confined to reads.

`Shutdown` (`supervisor.go:851-887`) deliberately copies the controller pointers under `s.mu.Lock()` and then stops them without holding `s.mu` (`:869-885`), so it does not amplify; that asymmetry is the shape of what the read path is missing. One site the Gate 24ae draft did **not** register is the mirror image of that safety: `ShutdownWithPersistence` (`:930-947`) holds `s.mu.RLock` (`:937`) across both `ctrl.Snapshot()` (`:939`) **and** `s.store.Update(…)` (`:941`), so it amplifies through the repository rather than through the controller — B+ removes only the `Snapshot` half of it, and it is registered as **OS-4** (§Out-of-scope findings), not fixed here (RV-10).

### Residual stall that this ADR does NOT remove

Even after the view migration, `InstanceService.ListInstances` (`internal/application/instance_service.go:140-165`) also reads the repository (`repo.ListInstances`, `repository.go:1382-1391`, `r.mu.RLock`), and the repository writer holds `r.mu` across the durable file write. So a status poll can still be delayed by milliseconds during a persistence operation. This is bounded, pre-existing, and out of scope: §Acceptance criteria require an observable `stopping`, not a latency bound. The same repository-side residual applies to **OS-4**'s `store.Update` under `s.mu.RLock` (`supervisor.go:941`) — after B+ the controller lock is out of that loop, the repository write is not. What B+ **does** remove, and what must not be described as a no-op, is the pair of unsynchronized reads in `wait()` itself (`:1862`, `:1865`) and the two unlocked `ic.instance.ModelID` reads in the log publishers (`:1879`, `:1894`); see §D5 and invariant **I-14** (RV-11).

## Decision

**Option B+ — one complete, immutable lifecycle snapshot per controller, published through `atomic.Pointer` inside every existing `ic.mu` critical section, with the lifecycle-state observation and arbitration readers migrated off `ic.mu`** (the narrowed scope that RV-3 requires; see the paragraph below and invariant I-3).

The view is *complete* because the readers are not: besides the instance payload, arbitration reads the published operation and the lifecycle readers read the current run, and `RemoveTerminal`/`ShutdownWithPersistence` persist from a snapshot (`supervisor.go:907-916`, `:936-947`). A partial projection leaves at least one `ic.mu.RLock` on the stop path, and one remaining `RLock` is enough to reproduce the failure. Atomicity alone buys nothing — the value of B+ is that **lifecycle-state observation and arbitration reads stop taking `ic.mu`**, which makes the writer's lock hold duration irrelevant to observability. Stated precisely, because Gate 24af RV-3 showed the absolute was too strong: the requirement is that **no lifecycle-state or arbitration reader can be blocked by `ic.mu` held across `stopCore`** — not that no code in the package ever acquires `ic.mu`. `cleanupRemovalProof` (`supervisor.go:437-461`) is the sanctioned exception: it is a mutation-adjacent removal proof that takes `ic.mu` for writing at `:438` because it also reads `preSpawnToken` (`:447`), a `launchMu`-guarded field that is deliberately **not** in the view (see §D5 and invariant I-3).

### D1 — The view and its field contract

```go
type lifecycleView struct {
    instance   domain.LaunchInstance // value copy, Args and Environment deep-copied
    generation uint64                // monotonic per-controller view counter
    run        *instanceRunState     // immutable pointer for that generation
    active     *launchOperation      // nil, or the operation published under arbLock
}
```

Field contract — the view must carry **everything today's `Snapshot()` returns plus what the other readers return**, because a reader must never need a fallback to `ic.mu`:

| Group | Fields | Source today |
|---|---|---|
| Identity | `ID`, `ModelID`, `ModelName`, `RuntimeID` | `domain/instance.go:80-83` |
| Attribution | `PipelineID`, `PipelineEntryID` | `domain/instance.go:85-93`; required by `compatible()` (`arbitration.go:204`, `instanceOwner` `:282-290`) |
| Observable lifecycle | `State`, `PID`, `StartedAt`, `StoppedAt` | `domain/instance.go:96-99` |
| Terminal detail | `ExitCode`, `ExitClass`, `LastError` | `domain/instance.go:102-104` |
| Frozen launch snapshot | `Executable`, `Args` (copied), `WorkingDirectory`, `Environment` (copied) | `domain/instance.go:107-110` |
| Metadata | `CreatedAt`, `UpdatedAt`, `RecoveryReason` | `domain/instance.go:113-115` |
| View-only | `generation`, `run`, `active` | `supervisor.go:1184-1211` |

Rules: a published `lifecycleView` is **never mutated** — construction happens under `ic.mu`, publication is a single `Store`, and readers use the returned pointer and its value copy as-is. `Args`/`Environment` keep the deep copies `Snapshot()` performs today (`supervisor.go:1736-1741`).

**One immutability rule (RV-2 — replaces the Gate 24ae draft's two contradictory sentences).** A published `lifecycleView` owns **immutable copies** of every mutable slice/map field it carries (`Args`, `Environment`); nothing in the view aliases controller-owned mutable data. A reader may consume those copies without another copy **only where the value it receives cannot be mutated by that caller**. Where a function hands a `domain.LaunchInstance` to a caller outside the package — `Snapshot()` is that function — the returned value must be either an independent copy or provably immutable to that caller; the two are distinguished explicitly:

| | Internal view | Domain snapshot returned to callers |
|---|---|---|
| Object | `lifecycleView.instance` (a value inside the published struct) | the `domain.LaunchInstance` `Snapshot()` hands back |
| Mutation by owner after publication | forbidden (I-2) | forbidden |
| Mutation by the **receiver** | impossible (the view is not exported) | happens today: handlers nil `Environment` before writing JSON (`handlers/instances.go:148`) |
| Consequence | may be shared by reference with in-package readers | must be an independent copy, or the receiver's mutation must be impossible |

So the slice contract is: deep copy at view construction (as `:1736-1741` does now), and **no alias to controller-owned mutable data may be handed to a caller that can write through it**. The Gate 24ae draft said both "never aliased into a reader" (I-5) and "no re-copy of already-immutable slices" (D5) — that pair is superseded by the single rule above.

**Live-pointer escape, stated honestly (RV-1).** The Gate 24ae draft asserted that "no reference to the live slices escapes". That is **false as written about the controller's own instance pointer**: `startCore` returns the live `ic.instance` on the residual-ownership error paths (`supervisor.go:1443` and `:1459`), and `startPostAdmit` forwards that same pointer to its caller when `startCore` fails (`:657-659`). Nothing at the baseline mutates it on those paths — the callers are `AdmitAndStart`/`start`, whose consumers in `internal/application` and the handlers check `err` before touching the value, and the handlers write only into their **own** copy of a snapshot (`handlers/instances.go:148`) — but that is a discipline enforced outside `internal/process`, not an invariant this package owns. The claim is therefore recorded as a **required design invariant of B+, not a satisfied fact**:

- **Invariant (I-13): no mutable controller-owned instance pointer escapes to an external caller in the implemented B+ design.** The two `return ic.instance` sites must return the published view's value copy (or `nil`) instead, so that a caller holding an error result cannot write through a pointer that the controller is still mutating under `ic.mu`.
- **Required source audit (beyond `internal/process`).** The D4 §4 scan alone cannot prove this, because the escaping pointer is *consumed* in `internal/application` and `internal/webui/handlers`. The implementation slice must therefore audit every consumer of `Supervisor.AdmitAndStart`/`start` error results and every writer of `domain.LaunchInstance` slice/map fields outside this package — the known case is `handlers/instances.go:148` (`inst.Environment = nil`), which is safe **only** because that handler operates on its own snapshot copy. A scan restricted to `internal/process` would pass while a future handler wrote through an escaped pointer.

This changes no secret-safety property: `Environment` is not persisted (`domain/instance.go:203-230`, ADR 016 D2) and handlers nil it before writing JSON (`handlers/instances.go:148`).

### D2 — Initial publication precedes registration

A reader must never observe a controller whose view is `nil`. Reachability has two distinct dimensions, and the Gate 24ae draft collapsed them into one sentence that also named the wrong file scope (AH-2): a controller's **operation claim** is published in one place, while the **registry insertions** that make a controller reachable happen at three sites in two files. Measured at the baseline, every `s.instances[...]` write that introduces or re-introduces a controller is:

| Path | Site | Lock | How this controller came to exist |
|---|---|---|---|
| Normal arbitration publication | `arbitration.go:269` — `s.instances[c.inst.ID] = c.ctrl`, reached only for `claimNewAdmission` (`:267`) | `s.mu.Lock()` (`:268`, released `:272`) | built by `newController` at the `AdmitAndStart` call site (`supervisor.go:608`) |
| Start test-seam registration | `supervisor.go:690` — `s.instances[inst.ID] = ctrl`, inside `Supervisor.start` | `s.mu.Lock()` (`:689`, released `:691`) | built by `newController` at `:687`; the seam's own doc comment (`:676-680`) states it is package-internal **TEST SEAM only** and that production code MUST use `AdmitAndStart` |
| `RemoveTerminal` re-insertion after a persistence failure | `supervisor.go:912` — `s.instances[id] = ctrl` | `s.mu.Lock()` (`:911`, released `:913`) | not a new controller: the one deleted at `:899` is put back because `s.store.Update` failed at `:909` (the error is still returned at `:914`), so the live view it carries already exists |

Separately, `publishClaimLocked` (`arbitration.go:264-273`) assigns the **operation** — `ctrl.active = op` under `ctrl.mu` at `:265` — which is D3 row 1, not a registry insertion; the two statements at `:265` and `:269` are one claim publication plus one insertion, not "two paths".

**Invariant to preserve across all three insertions (I-4): a controller must have a valid initial immutable view before becoming reachable through any registry insertion path.** The first two paths construct through `newController` (`supervisor.go:1245-1252`) → `NewInstanceController` (`:1255-1266`), and the third re-inserts a controller that already went through them, so publishing the initial view inside `NewInstanceController` covers all three paths and **no insertion site needs its own publication**. Note the ordering this makes explicit: a controller is registered, and its `pending` state is readable, **before** the durable pending record is created (`supervisor.go:639-647`). This correction changes no registration behavior, adds no registration path, and authorizes no new slice.

### D4 — Non-bypassable mutation helpers, and the reachability proof

Mutations move into package-private helpers that own exactly one responsibility — mutate under `ic.mu`, then publish — so "forgot to publish" is a structural impossibility rather than a review finding:

Reachability proof, worked backwards from the effect the fix must produce ("a reader observes `stopping` while the process is alive"):

1. The observable effect is produced by exactly one of the read primitives: `Snapshot()` (`supervisor.go:1731-1743`), `IsRunning()` (`:1269-1273`), `GetControllerDone()` (`:1989-1999`), `currentRun()` (`:2001-2008`), `activeOperation()` (`arbitration.go:352-356`), `revalidateOperation()` (`:372-380`). After migration, each of these resolves the atomic pointer only; none acquires `ic.mu`. `GetDoneChannel()` (`:1977-1982`) already takes no controller lock and stays as it is. Two inline readers exist outside those primitives and are enumerated in §D5 rather than left to chance: the `ic.mu.RLock` region in `restartWithRefresh` (`supervisor.go:1666-1669`), which migrates to the view, and `cleanupRemovalProof` (`:437-460`), which keeps `ic.mu` because it also reads `preSpawnToken` — a `launchMu`-guarded field that is deliberately **not** in the view.
2. Therefore a **migrated** reader can be delayed **only** by a value it reads that is not in the view. The view is complete (D1) for every field the migrated readers need, so none of them has such a field left. The one reader that keeps `ic.mu` by design — `cleanupRemovalProof`, for `preSpawnToken` — is excluded from this step on purpose and is not claimed to be non-blocking; it is reachable only from `ForgetCleanedControllers`, never from a lifecycle-state read (RV-3).
3. Therefore a stale read can be produced **only** by a mutation that did not publish. Every production mutation of the fields in D1/D3 is one of rows 1-18 — these are the only mutations of `ic.instance.*` (whether by direct assignment or by a call to `UpdateState`/`UpdateError`/`Fail`), of `ic.run` and of `ic.active` on production paths at the baseline, and they live in `internal/process`, which owns the controller structs per AGENTS.md §File ownership — and each of those rows is inside an `ic.mu`/`ctrl.mu` region that the corresponding helper takes; the one test-support assignment, `arbitration.go:448-450`, is handled by the explicit allow-list of §D3. One qualification Gate 24af RV-1 makes mandatory: the enumeration covers **controller-owned** mutations, and it is complete only because no external package can reach `ic.instance` — which in turn depends on the escape of the live pointer being closed (I-13, §D1). Until that is closed, "a stale read requires an unpublished mutation" also admits the weaker case of an external writer holding the escaped pointer.
4. Control: a package test that scans the `internal/process` sources and fails on an **unpublished mutation** — a mutation of a D1/D3 field that is not one of the inventoried publication sites and not an exact allow-list entry. Gate 24ah AH-1 establishes that this obligation covers **both** mutation forms the code actually uses, and that naming only one of them would leave the control blind:
   - **(a) direct assignment** to controller-owned lifecycle state — writes to `ic.instance.<field>` / `ctrl.instance.<field>` (the `x.State = …` form at `supervisor.go:1815`, `ExitClass`/`LastError` at `:1810`/`:1812`, `PID`/`StartedAt` at `:1409-1410`, the restart-spec block at `:1693-1699`), plus `ic.run` (`supervisor.go:1368`) and `ic.active` (`arbitration.go:265`, `:365`);
   - **(b) a call to a mutating method on a controller-owned instance receiver.** `domain.LaunchInstance`'s complete pointer-receiver mutating set is exactly three methods — `UpdateState` (`internal/domain/instance.go:149`), `UpdateError` (`:172`), `Fail` (`:181`); the other pointer-receiver methods (`IsLive` `:121`, `IsInFlight` `:127`, `IsRunningOrStarting` `:133`, `IsTerminal` `:139`, `EnvironmentToList` `:190`) are readers. Eleven call sites exist in `internal/process` today, all on `ic.instance`/`ctrl.instance`: `supervisor.go:263`, `:294`, `:1359`, `:1394`, `:1411`, `:1503`, `:1524`, `:1526`, `:1532`, `:1559`, `:1623` (measured by scanning every `*_test.go` too: none of them calls these three methods, so the method-call form is currently production-only).

   Why the second form is not optional: D3's rows are mixed — rows **3, 5, 8, 9, 10, 11, 17, 18** mutate *only* through one of those three methods, rows **6** and **7** pair a method call with direct field writes (`:1409-1411`, `:1503-1504`), and rows 1, 2, 4, 12-16 write fields directly. Counted as rows, **ten of the eighteen** contain at least one method call — `supervisor.go:263`, `:294`, `:1359`, `:1394`, `:1411`, `:1503`, `:1524`, `:1526`, `:1532`, `:1559`, `:1623`, i.e. eleven call sites, because row 9 has two. An assignment-only scan would therefore miss every mutation in the eight method-only rows and miss the state write in rows 6 and 7 while still seeing their `PID`/`StartedAt`/`LastError` lines, so a future `ic.instance.UpdateState(domain.InstanceStateStopping)` written without a following publication would pass it. The repository already accepts source-scanning controls of this shape (`TestI18nDictionariesParity`, `internal/webui/server_test.go:33`), and the same blind spot that test has is recorded as debt in `UI-I18N-01` — the two forms are both required precisely so the control does not inherit that debt.

   **What the scan is not (AH-1).** It must not be described as proof that no other mutation exists. The obligation is therefore an **auditable approach** of which the scan is one mechanism, with six requirements, each checkable at a gate:

### D6 — Generation identity and publication ordering

A controller is reused across generations (`restartWithRefresh` never constructs a new one; it stops the old run at `:1671` or awaits it at `:1674-1684`, refreshes the spec at `:1691-1699`, then spawns). The view therefore carries `generation`, bumped under `ic.mu` on every publication, and `run` — the pointer that makes a view's generation identifiable. Ordering rules, unchanged by atomicity and stated because atomicity does not provide them:

- `lifecycleMu` serializes start/stop/restart per controller (`:1293-1295`, `:1541-1542`, `:1651-1652`), so publications from different operations on one controller are totally ordered. **Atomicity provides no such order; the mutex does.**
- `run.done` (`:1219`, closed by `complete()` at `:1232-1234`) is the barrier between generations: a new generation's `starting` publication is reachable only after the previous run completed (or after a rollback left ownership with `wait()`, in which case no new generation may start — ADR 016 C/D).
- Consequence: an older generation cannot overwrite a newer view, because the older writer is barred from `ic.mu`-held work after the newer one starts by these two locks. The view is a projection of state that is already ordered; it must not be described as the thing that orders it.

### D10 — Persistence consistency model

**Lock-order dependency (RV-13).** [ADR 017 §Lock Ownership and Ordering](017-unified-launch-arbitration.md) documents the project's **complete lock order** at `017-unified-launch-arbitration.md:196-207`: `s.arbMu` → `s.arbLocks[modelID]` → (`r.mu`, `s.mu`) → `[arbLocks released]` → `s.semaphore` → `ic.lifecycleMu` → **`ic.mu` (`:205`)** → `r.mu` (`:206`). B+ does **not** change any edge of that write-side order: no lock is added, removed, acquired in a new sequence, or held across a new boundary, and `ic.mu` still nests inside `ic.lifecycleMu` exactly as that table states. What changes is only the **read-side dependency** the order was implicitly carrying: readers that today sit *behind* `ic.mu` (including `scanConflicts` under `s.mu` and `checkRestartTarget` under `arbLocks`) stop acquiring it, so they inherit no edge of the order at all. The consequence must be recorded honestly in both directions — the arbitrating path is *shorter*, because a `stopping` instance is no longer a transitive blocker inside `arbLocks` (`arbitration.go:155-157`, `:316`) or inside `s.mu.RLock` (`:197`, `:201`), and the *invariant* that the write-side order guarantees is unchanged. ADR 017's own text is not amended by this ADR; reconciling it is slice 4's obligation (above).

**Explicit decision: persistence ordering is not changed by this ADR.** No `persist-before-wait` is introduced, no persist moves outside an existing lock region, and the durable sequence stays:

```
pending (:639-647 store.Create) → starting (:1370) → running (:1418, ADR 016 S1/S2)
        → stopping (:1587, AFTER Manager.Stop returned) → terminal (:1630 or :1831)
```

The live and durable views of a stop therefore differ, deliberately and temporarily:

| Interval | Live (view) | Durable (repository) |
|---|---|---|
| Process alive, graceful/force stop in progress | `stopping` | `running` with the full running identity |
| Process exited, before `:1587` commits | `stopping` | `running` |
| After `:1587` | `stopping` | `stopping` |
| After `wait()` publishes terminal and one persist succeeds | `exited`/`failed` | `exited`/`failed` |

- **Crash behavior (unchanged):** a crash in the first two rows leaves `running` + live PID; `Recover` sees `IsInFlight()` and `classifyForRecovery` returns `stale`/`pid-not-found` for a dead PID (`supervisor.go:1062-1074`). A crash after `:1587` leaves `stopping`; the same path classifies it `orphan` only if the process is alive and identity-confirmed (`:1081-1085`), else `stale`. Nothing in B+ moves these boundaries, because nothing in B+ moves a persist.
- **Terminal authority:** memory stays authoritative (ADR 016 T3); a failed terminal persist leaves the durable record at the last successful state and recovery reconciles it (T5) — `:1834-1852` documents and implements exactly that, and it is preserved.
- **Persistence failure:** `:1588-1591` still returns the persist error to the caller with `stopErr` dropped, and `wait()` still finalizes the run on exhaustion (T1/T2). B+ publishes the view *before* the persist attempt in each helper, so a failed persist cannot leave an unpublished state change — the live view is deliberately ahead of the durable record in the same window it is ahead today.
- **Audit:** unchanged, and it inherits the improvement rather than a change. Both stop handlers log `EventInstanceStop` **after** the synchronous stop returns (`handlers/instances.go:130`, `handlers/models.go` writes `{"status":"stopped"}` at `:279`), so audit keeps one record per completed stop. Because the model-route lifecycle writes no audit record at all (a fact already carried by the MA-06 gate records), this ADR does not claim audit coverage for that route.
- **Compatibility:** `docs/API.md:119` (the `POST /api/v1/instances/{id}/stop` row with its `409`/`launch_in_flight`), `docs/API.md:159-163` (the in-flight body), `docs/API.md:174-191` (the lifecycle error-mapping table) and ADR 016's S1/S2 persistence invariants (`016-durable-lifecycle-ownership.md:344-345`), ADR 017's `stopping`-allow rule and the orphan/stale recovery contract all keep their current wording. `docs/API.md:157`'s one-in-flight-per-model rule stays true because `IsInFlight()` still includes `stopping`. This ADR changes what is *readable*, never what is *written* or *decided*.
- **Documentation reconciliation obligation (RV-13):** the doc-reconciliation slice (slice 4) must update **`docs/adr/017-unified-launch-arbitration.md`** in addition to `docs/API.md` and `docs/ARCHITECTURE.md`. ADR 017 is **not** modified by this document, and its arbitration semantics are untouched — but its **lock-order section is amended on the read side by B+**, so leaving it uncited would make the two records contradict each other once slice 2 lands.
- **Pipeline aggregate route is not an observation surface (RV-7).** `GET /api/v1/pipelines/{id}` derives each entry's `state` from `inst.IsRunningOrStarting()` (`internal/webui/handlers/pipelines.go:186`), and that predicate is `starting | running` only (`internal/domain/instance.go:131-135`); the field defaults to `"stopped"` at `:176` and only `orphan` is recovered afterwards (`:196-204`). **A `stopping` instance therefore reports `stopped` on that route at the baseline and will still report `stopped` after B+** — B+ changes no predicate and no aggregation, and this ADR does not claim the aggregate pipeline state itself becomes `stopping`. The browser nonetheless shows `stopping` for a pipeline entry, because the client derives entry and aggregate status from the **instances collection**, not from that route: `pipelineEntryStatus` filters `instancesData` by `pipeline_id`/`pipeline_entry_id` (`internal/webui/static/app.js:670`, `:671`, legacy fallback `:673-679`), keeps `stopping` as active (`isActive` `:335`), and selects it at `:688`; `pipelineAggregateStatus` propagates it at `:725`; `pipelineChips` renders the badge (`:703-716`, `:709`) and `pipelineStateBadge` the same (`:732-734`). The model row path is the equivalent for a manual stop (`modelStatus` `:337-343`, `stopping` at `:343`). So the admissible observation surfaces for **every** F-7 leg, manual or pipeline, are `GET /api/v1/instances` (`handlers/instances.go:49-61`), `GET /api/v1/instances/{id}` (`:62-77`) and the DOM badges those produce — never `models[].state` on the pipeline route.

### D11 — API and UI behavior

- `Stop` remains synchronous; no `202`, no new endpoint, no new field, no new state string, and `domain.LaunchInstance`'s JSON shape is untouched (`domain/instance.go:79-116`).
- The Web UI already renders `stopping` (`app.js:335`, `:337-343`, `:556`; pipeline derivation `:688`, `:725`, both computed from `instancesData` at `:670-671` — see §D10 RV-7) and refreshes on a 3000 ms timer (`:2360-2364`); no client change is required or authorized. No synthetic "stopping" badge may be introduced client-side — the requirement is that the **server** reports it.
- **The visible window is not guaranteed to contain a poll (RV-8).** After B+ the badge becomes *renderable*, but the observable duration is still the real stop duration: `Manager.Stop` returns as soon as the process exits (`manager.go:239`), which for a fast-shutting runtime can be well under the 3000 ms refresh period at `app.js:2358-2364`; the 5 s force-kill (`:242-244`) and the 15 s cap (`supervisor.go:1576`) bound the other end. A human observer whose page happens to poll between two state changes can therefore miss the badge **even when the backend produced and served it correctly**. The consequence for acceptance design is stated in the acceptance contract's F-7.5 and §F-7.5 correlation and dwell requirements below, and it is a measurement problem, not a product defect: **a missed poll may never be recorded as a product FAIL.**
- No artificial production delay may be added to make the state visible — no dwell is permitted in production code. The only permitted seam is §Test-only stop gate, and it exists so that the *deterministic test* can hold the window; it must not be described as making the window observable to a human. The human leg gets its window from the fixture's real graceful-shutdown duration, subject to the prerequisite in the next bullet.
- **The Windows `stopping` dwell capability is NOT YET PROVEN (Gate 24ah AH-4).** Revision 2's T-9 asserted that a real multi-second stopping interval is "achieved by fixture choice". On Windows no measurement in this repository supports that, so the assertion is withdrawn and replaced by an explicit prerequisite, with the mechanism stated at the strength the bytes give: **(1)** `windowsControl.GracefulStop` sends `CTRL_BREAK_EVENT` through `GenerateConsoleCtrlEvent` and returns `nil` only when that call succeeds (`internal/platform/platform_windows.go:106-116`); when it does not, the same function **escalates immediately to `ForceKill`** (`:118-122`), and its own comment names the case — a process with no console cannot receive a console control event; **(2)** so in a failed-delivery run there may be **no useful `stopping` interval at all**: `Manager.Stop` waits `done` (`internal/process/manager.go:239`) and only if that does not fire within 5 s force-kills (`:242-244`), meaning a force-killed run yields process teardown, not a graceful dwell, and the UI's 3000 ms poll (`internal/webui/static/app.js:2360-2363`) may have nothing to land in; **(3)** the existing fake-runtime modes must **not** be assumed sufficient: `graceful` returns as soon as a signal arrives (`testdata/fake-runtime/fake.go:166-170`), `ignored-signal` ignores SIGTERM and exits on SIGINT (`:172-188`) — and SIGTERM is not a Windows console signal, so its Windows behavior is itself unmeasured — while `delayed` never waits for a stop signal at all and exits on its own timer (`:190-206`), which cannot certify a dwell *caused by* a stop; **(4)** a **dedicated test-only fixture behavior may be required**, and any such behavior must drive the **real OS process lifecycle** and must never fabricate or inject a `stopping` API response — the acceptance requirement for real process liveness (F-7.2, AC-2, identity via `GetProcessIdentity`) is not weakened by this finding; **(5)** the Windows console-control delivery path must be **accounted for explicitly** in whatever gate proposes the fixture; **(6)** where `GenerateConsoleCtrlEvent` fails and the process is killed immediately, an unobserved badge is **NOT OBSERVED / INCONCLUSIVE**, never a product FAIL; **(7)** the dwell capability must be **demonstrated by measurement in a separately authorized preparation gate before any Owner UI leg is scheduled** — scheduling a human observation leg on an assumed window is what this finding forbids; **(8)** this bullet prescribes **no fixture implementation**, claims **no working Windows dwell**, and introduces no production delay, no synthetic UI state and no altered `Stop` semantics. It is a prerequisite on a later gate, not an implementation authorization; the Linux path is not covered by this bullet either — its dwell is likewise unmeasured, and only the deterministic Go test (T-1…T-7, which uses the seam rather than a fixture dwell) is unconditional.
- `GET /api/v1/instances` (`handlers/instances.go:49-61`) and `GET /api/v1/instances/{id}` (`:62-77`) are **the** observation surface for the acceptance legs, in both the manual and the pipeline case. `GET /api/v1/pipelines/{id}` is **not** admissible for proving live `stopping` (§D10 RV-7).

## Test-only stop gate

**Proposed, documented here, NOT implemented.** Its purpose is to make the F-7 assertion deterministic: a test must be able to hold a stop in the window where the state is `stopping` and the process is alive, read it, and then let the stop complete.

- **Shape:** a package-private injection point on `Manager` that the stop path consults *after* the graceful signal and *before* returning — e.g. a `stopGate func()` field read and invoked inside `Manager.Stop` near `manager.go:227`. It follows the two seams `Manager` already carries: `killOverride` (`:280-285`, installed by `SetKillOverride` at `:293-297`) and `startOverride` (`:300-304`) — same package-private field, same `m.mu`-guarded assignment style. The existing pair proves the repository's convention for a stop/start seam; B+ adds one in the same shape.
- **Default:** `nil`. When `nil`, the stop path is byte-for-byte the current path: no waiting, no channel, no allocation on the happy path, and no changed ordering. Production behavior must be provably identical with the seam present — that is an acceptance obligation, not an assumption (§Deterministic test obligations, T-6).
- **Not allowed:** a new exported API; any `time.Sleep` in production code; a gate that is enabled by configuration or environment; a gate that changes what is persisted or in what order; a delay long enough to be observable by a human user.
- **Synchronization:** the test installs a gate that signals "I am inside the stop" on a channel and blocks on a second channel until the test says proceed. Barriers and channels, never sleeps — required because `internal/process` tests already contain 26 `time.Sleep` calls across at least 10 files, which is precisely the pattern that cannot certify a sub-second window.
- **Watchdog:** a deadline may only convert a hang into a **FAIL**; it may never stand in as the observation. A test that passes because its watchdog fired is a FAIL.
- **Scope of the seam:** it exists so the test can prove `stopping` is readable before exit. It does not change lifecycle semantics for any caller and must not be reused by any other test as a general stop-delay tool. **It is not an acceptance convenience (RV-8):** the browser leg must not be run against a binary whose window was widened by the seam, because then the observation would prove the seam, not the product. The human leg gets its window from the fixture's real graceful-shutdown duration (T-9) — and Gate 24ah AH-4 records that **that capability is not yet proven**, least of all on Windows, so the fixture must be demonstrated in a separately authorized preparation gate before an Owner UI leg is scheduled (§D11 AH-4 bullet).

## Deterministic test obligations

Each is an obligation on the later implementation gate; none is authorized by this ADR.

- **T-1 (core):** with the stop gate held, `GET /api/v1/instances/{id}` and `GET /api/v1/instances` each return `state: "stopping"` while the fake-runtime process is still alive, then release and observe the terminal state. Liveness must be proven by **process identity, not PID alone**, using three distinct declarations that revision 2 cited at their comment lines (AH-3): the **process liveness function** `platform.RecoveryProber.IsProcessAlive(pid)`, declared at `internal/platform/recovery.go:16` (comment `:15`); the **process identity function** `GetProcessIdentity(pid)`, declared at `:20` (comment `:18-19`); and the **process identity type** `ProcessIdentity{ExecutablePath, StartTime, HasStartTime}`, declared at `:6-10` with fields at `:7`, `:8`, `:9`. The distinction matters for the evidence, not just for the numbering: `IsProcessAlive` answers "does this PID exist", which a recycled PID can satisfy, while `GetProcessIdentity` returns the executable path and start time that the check actually compares. The executable path is compared against the instance's frozen `Executable` (`domain/instance.go:107`), and `StartTime`/`HasStartTime` are used wherever the platform supplies them (the same comparison the recovery path already performs in `verifyIdentity`, `supervisor.go:1090-1105`: executable paths must match, and `StartTime` is consulted only when `HasStartTime` is true and the instance's `StartedAt` is set), so a recycled PID cannot be mistaken for the managed process. The run's `managerDone` channel not being closed is a corroborating in-test signal, not the liveness proof.
- **T-2:** the same read via `Supervisor.List`, `Supervisor.Status`, `InstanceService.ListInstances` and the handlers — one test per layer, so a regression in one cannot hide in another.
- **T-3 (non-stall):** while instance A is inside the held stop, a `Snapshot`/`scanConflicts`-driven arbitration for **another** model completes without blocking; assert on ordering, not wall-clock.
- **T-4 (no state inversion):** Stop ∥ Stop, Stop ∥ Restart and Start ∥ Stop interleavings around the gate produce exactly the D9 outcomes. Per RV-6 the Stop ∥ Stop assertion must be stated as **the three properties separately** — `lifecycleMu` serialization, single `cmd.Wait()` owner, and (for the non-timeout case) the second call returning without taking stop ownership — and must **not** assert at-most-once `Manager.Stop` invocation, which the code does not guarantee after the 15 s context expiry (`supervisor.go:1613-1617`, `:1637`; OS-5). A test that merely proves `lifecycleMu` serialization must not be reported as proving OS-5 away.
- **T-9 (browser-leg fixture, RV-8; dwell capability NOT YET PROVEN, AH-4):** the human observation leg needs a stopping interval a person can actually see, and production code may not be slowed to provide one. The requirement stands unchanged: the controlled fixture must obtain a **real** multi-second `stopping` window from the runtime's own behavior, so `Manager.Stop` genuinely waits at `manager.go:239` and the interval exceeds the 3000 ms UI poll (`app.js:2358-2364`), never by a production sleep or a dwell flag (both forbidden in §Test-only stop gate), and the fixture's chosen interval must be recorded in the evidence. What revision 2 added — "This is achieved by fixture choice", illustrated by "a fake runtime that acknowledges the graceful signal and exits after a delay" — is **withdrawn as an unproven assumption** and replaced by a prerequisite: **no existing fake-runtime mode is measured to produce such a window, and none may be assumed sufficient** (`graceful` returns as soon as a signal arrives, `testdata/fake-runtime/fake.go:166-170`; `ignored-signal` ignores SIGTERM and exits on SIGINT, `:172-188`, and SIGTERM delivery is not a Windows concept; `delayed` never waits for a stop signal and exits on its own timer, `:190-206`, so it cannot certify a dwell *caused by* the stop). On Windows the delivery path itself can defeat the window: a failed `GenerateConsoleCtrlEvent` escalates straight to `ForceKill` (`internal/platform/platform_windows.go:118-122`), and in that run a useful `stopping` interval may simply not exist. Therefore T-9 now carries four obligations on later gates and **no implementation of its own**: (i) the dwell capability must be **demonstrated by measurement in a separately authorized preparation gate before any Owner UI leg is scheduled**; (ii) if no existing mode suffices, a **dedicated test-only fixture behavior may be required** — this ADR does not prescribe its shape; (iii) any such behavior must drive the **real OS process lifecycle** and must **never fabricate or inject a `stopping` API response**, so the real-liveness requirement of T-1/F-7.2 is not weakened; (iv) the Windows console-control delivery path must be **accounted for explicitly** wherever the fixture is proposed. Where the window is missed by the browser, or where the console-control delivery failed and the process was killed immediately, the disposition is **NOT OBSERVED / INCONCLUSIVE**, never a product FAIL (acceptance contract §16).
- **T-5 (durability unchanged):** assert the durable record is still `running` at the moment the live view reads `stopping` (D10 row 1), and that the sequence `pending → starting → running → stopping → terminal` is preserved.
- **T-6 (seam inertness):** with no gate installed, the stop path's observable behavior and persist call count are identical to the baseline.
- **T-7 (control):** the source-scanning test of D4 item 4 fails on an injected direct `ic.instance.State = …` outside a helper **and** on an injected `ic.instance.UpdateState(domain.InstanceStateStopping)` call outside a helper — per `UI-I18N-01`'s lesson the assignment form must be tested as the *direct-write* form, and per Gate 24ah AH-1 the method-call form must be exercised too, because ten of D3's eighteen production rows mutate through `UpdateState`/`UpdateError`/`Fail` (eleven call sites, §D4 item 4) and an assignment-only control would pass a new unpublished method-call writer. The test must additionally assert that the **detected set still equals the inventoried set** (§D4 item 4, requirement 4), so a site whose publication silently disappears fails as loudly as a new one.
- **T-8:** the maintained browser suite gains a portable-lifecycle leg only in a later slice, per the acceptance document; race evidence must come from the Linux CI job (`CGO_ENABLED=1 go test -race -timeout 20m ./...`), because local `-race` is unavailable on this workstation.

## Rollback considerations

- Slices 1-2 are additive-in-place but touch every lifecycle read, so the rollback unit is **one revert of the whole slice**, not a feature flag; this ADR forbids introducing a flag or a compatibility shim to keep both read paths alive (a dual path would make invariant I-3 unprovable).
- The view carries no durable state, so reverting needs no data migration and no store-format change; `ToStorageEntry`/`ToDomain` are untouched.
- If a slice is published and later found defective, the correction follows the full cycle (correction → verification → Commit Gate → Publication Gate); a previous authorization never extends to a correction or a new SHA.
- Slice 3 can be reverted independently of 1-2 only if the reader migration in slice 2 is a no-op for tests; that must be verified at the slice-2 gate, not assumed.

## Acceptance criteria

Numbered for the acceptance document, which is the record of whether each was met. **None is met by this ADR.**

- **AC-1** A real `stopping` state is produced by the backend on a manual stop (API + store + audit evidence).
- **AC-2** `GET /api/v1/instances/{id}` and `GET /api/v1/instances` return `state: "stopping"` **while the managed process is alive**, in a deterministic test and in a browser observation. Liveness is proven by process **identity** (`GetProcessIdentity`, T-1), and the state read, the identity check and the browser receipt must be shown to belong to **one and the same controlled stop interval** — not to three unrelated observations (§D11, RV-8; acceptance contract F-7.5).
- **AC-3** The Web UI renders the `stopping` badge for that interval, RU and EN, with no client-side fabrication. A badge rendered **after** the process exited does not satisfy this criterion, and a badge missed because the 3000 ms poll did not land inside a short real window is recorded as **NOT OBSERVED**, never as a product failure.
- **AC-4** Process termination then yields `exited`/`failed` consistently in API, store and UI.
- **AC-5** No new `orphan`/`stale` divergence appears on stop, restart, crash-after-stop or shutdown.
- **AC-6** Repeated `Stop` on the same instance stays safe and never creates a second **owner of the same run**. Scoped exactly: this criterion does **not** claim at-most-once `Manager.Stop` invocation after the 15 s context expiry — that case is forensic question OS-5 and is outside F-7 (RV-6).
- **AC-7** Concurrent lifecycle arbitration (Stop ∥ Restart, Start ∥ Stop, cross-model) is unchanged in decision and no longer stalls behind a stopping instance.
- **AC-8** `Stop` remains synchronous: `200 {"status":"stopped"}` after completion, no `202`, no new fields.
- **AC-9** Persistence ordering is unchanged: no persist moved, added, removed or reordered; live `stopping` with durable `running` is permitted exactly as today.
- **AC-10** Pipeline-initiated stop shows the same observability as a manual stop **on the admissible surfaces** — `GET /api/v1/instances`, `GET /api/v1/instances/{id}` and the DOM badges derived from `instancesData` (`app.js:670-671`, `:688`, `:725`). `GET /api/v1/pipelines/{id}` must **not** be used as evidence and must **not** be changed: its `models[].state` gates on `IsRunningOrStarting()` (`handlers/pipelines.go:186`, `domain/instance.go:131-135`) and reports `stopped` for a `stopping` instance both before and after B+ (RV-7).
- **AC-11** Windows and Linux are both exercised; race evidence comes from the Linux CI job with the literal race command. Because §D5/RV-11 records that B+ deliberately removes unsynchronized reads, the CI race result is part of AC-11's meaning: it confirms the removal, and no local `-race` claim may substitute for it.
- **AC-12** Full required checks plus the maintained browser suite pass for the exact published SHA, with results recounted as raw `PASS |` / `FAIL |` lines rather than summed `TOTAL` lines.

## Out-of-scope findings

Recorded, not fixed, and not authorized here. Each is a repository fact at the baseline; **none carries a claim of confirmed runtime impact**, and each needs its own forensic before any change. They must not be folded into a B+ slice.

- **OS-1 — terminal `ExitClass` can be replaced by `error` after the real class was derived.** `wait()` derives `ExitClass` from the process exit at `supervisor.go:1807`; `stopCore` then calls `ic.instance.UpdateError(stopErr, domain.InstanceExitError)` at `:1623` whenever `stopErr != nil`, and `domain/instance.go:172-175` shows `UpdateError` assigns `ExitClass` unconditionally. The two writes are separated by the `run.done` synchronization, so an ordering that replaces the real class exists in the bytes; whether it is reachable in practice, and whether the resulting `error` class is then persisted by the final `:1630` write, is **unproven at this gate**. Classification: finding requiring separate investigation (class C).
- **OS-2 — the late `LastError` append after terminal-persist exhaustion is never persisted, so the durable record and the live view can differ permanently in `LastError`.** `wait()` appends the persistence-exhaustion error to `ic.instance.LastError` at `:1846-1850` **after** the terminal entry was already captured and persisted (or attempted) at `:1823`/`:1831`, and no later write carries it: the only subsequent persist of this controller is `stopCore`'s final persist at `:1630`, which is reached only in the ordering where the terminal append already happened *before* it, and the next generation's persists start from whatever `restartWithRefresh` publishes. So the divergence between the durable record and the in-memory view is the finding. **What the Gate 24ae draft additionally claimed — that the append can land "across a run boundary", i.e. inside a newer generation's ownership window — is NOT supported and is withdrawn (RV-5).** The append happens at `:1846-1850` while `ic.mu` is held (taken at `:1845`), and `run.complete()` is the **final statement of `wait()`** at `:1869`; `restartWithRefresh` may publish a new run only after `ic.stop(ctx)` returns (`:1671`) or after it observes `previousRun.done` (`:1674-1684`, select on the closed channel at `:1680-1682`), and both paths are further serialized by `lifecycleMu` (`:1651-1652` vs `:1293-1295`/`:1541-1542`). Since closing `run.done` happens-after the append, a generation that starts through either of those two paths cannot be in flight while the append runs. **The one path that is not excluded by that argument is the 15 s context-expiry path** (`supervisor.go:1613-1617`, where `stopCore` returns without observing `run.done`) — and if a restart followed it, a crossing would be reachable. That path is precisely unresolved case **OS-5** below, so OS-2's withdrawal is stated to the strength the bytes give: the run-boundary crossing is **not established** (hence it may not be recorded as a defect), and it is **not excluded in every ordering** either. The remaining, separately supported concern is that the serialization does **not** cover `RemoveTerminal` (`:895-908`), which reads and persists a snapshot under `s.mu` only (`:907-916`, re-insert `:912`) — so a store-side `LastError` written by that path can still disagree with the live view. **Impact unproven; needs its own forensic. No repair task is opened for the withdrawn run-boundary claim.** Classification: class C.
- **OS-3 — lock-order documentation contradicts one call site.** `failUnspawnedController` documents that the mutation and snapshot are taken under `ic.mu` and "the repository write runs AFTER the unlock because repository implementations hold their own lock across the file write and must never be nested under `ic.mu`" (`supervisor.go:285-287`). `abortPreSpawnCleanup` calls `s.store.Update(...)` at `:265` **inside** its `ctrl.mu.Lock()`/`Unlock()` region (`:262-267`). This ADR follows the documented rule for its helpers and changes nothing at either site. Classification: class C documentation/consistency finding.
- **OS-4 — `ShutdownWithPersistence` holds the registry read lock across repository I/O (RV-10).** `s.mu.RLock()` at `supervisor.go:937` is held for the whole loop, which calls `ctrl.Snapshot()` at `:939` and `s.store.Update(domain.ToStorageEntry(&snap))` at `:941` before `s.mu.RUnlock()` at `:946`. Two stalls compose here, and only one of them is B+'s business: **B+ removes the controller-lock dependency** — after migration `:939` resolves the atomic pointer, so a controller inside `stopCore`'s long `ic.mu` hold can no longer extend this registry walk — while **the store-I/O portion remains**: the repository lock is still taken across a file write inside `s.mu.RLock`, exactly as §Residual stall describes for the read side (`repository.go:1346-1358`). This is the second amplification site §The amplification did not register in the Gate 24ae draft, and it is registered here rather than silently absorbed: **changing that locking behavior is outside F-7's scope**, it needs its own forensic, and no implementation slice of this ADR may "improve" it. Classification: class C.
- **OS-5 — unresolved case: a second `Stop` after the first times out may invoke `Manager.Stop` again (RV-6).** The sites: `supervisor.go:1548-1557` guards only terminal and `pending`, never `stopping`; `:1613-1617` returns from `stopCore` on the 15 s context expiry **without** observing `run.done`, leaving the state at `stopping`; `:1637` returns `ctx.Err()`; and `manager.go:214-267` has no stop-once guard — its only early return is `m.cmd == nil` (`:216-219`) — so a second call re-signals `GracefulStop` (`:227`) and re-arms the 5 s `ForceKill` (`:242-244`). **This is recorded as a forensic question, explicitly not as a confirmed production defect:** no test was executed here, local `-race` is unavailable on this workstation, and whether the second call is reachable in practice (and whether a repeated `GracefulStop`/`ForceKill` has any user-visible effect, given `syscall.ESRCH` is tolerated at `:245`) is unproven. Consequences if confirmed would be ADR-016-adjacent (stop ownership vs. signal emission) and would need their own design gate. **F-7 must not be expanded to repair it**, and F-7.9/AC-6 stay scoped to what B+ actually guarantees (§D9). Classification: class C, needs its own read-only forensic.

## Consequences

**Positive:** a synchronous stop becomes observable while the process is alive; the registry-wide stall of §The amplification is removed as a side benefit; and the controller's read surface collapses onto one immutable projection, which makes "what a reader may see" a single reviewable object.

**Costs and risks:** the D1 field set must be complete on day one, because a missing field forces a fallback `ic.mu` read and re-creates the defect invisibly (this is what falsified narrow B); the 18 production publication sites become load-bearing, so the source-scanning control is part of the contract and not an optional extra — and after RV-4 that control must scan the package's test writers too, not only production files, because five of them already mutate the same fields, while after AH-1 it must cover **both** mutation forms (direct assignment **and** the three `*domain.LaunchInstance` mutating methods, which appear in ten of the eighteen rows at eleven call sites) and must be described as an auditable control rather than as proof that no other mutation exists (§D4 item 4); the live-pointer escape (§D1 RV-1) must be closed in slice 1 or invariant I-3's premise ("no external package can reach `ic.instance`") stays unproven; `Snapshot()`'s copy shape changes (it stops deep-copying per call and returns an already-immutable value), which needs explicit review against `docs/ARCHITECTURE.md` and against the handler that nils `Environment` (`handlers/instances.go:148`); and every existing lifecycle test in `internal/process` remains valid only if the arbitration decisions are untouched — ADR 017's D-series tests are the guard for that.

**Changed on purpose, and therefore not advertised as "no observable change" (RV-11):** B+ removes the unsynchronized reads at `supervisor.go:1862`/`:1865` and the unlocked `ic.instance.ModelID` reads at `:1879`/`:1894`. The first pair sits in the same window in which `stopCore` can lock and write `ExitClass`/`LastError` after a context expiry (`:1621-1624`), so the bytes admit a concurrent unsynchronized read against a locked write; eliminating it is a **safety property of the migration**, not a neutral rewrite, and the claim is deliberately narrower than "nothing changes": what the implementation must prove is that the migrated reads return the same values as the locked reads **under valid execution ordering** (T-4, T-6), and that Linux CI `-race` is clean for the published SHA (F-7.13). No race was reproduced by an executed test at this gate, and none may be reported as if it had been.

**Not changed, deliberately:** persistence ordering, terminal authority, single `Wait` ownership, arbitration decisions, the synchronous `Stop` contract, the `pending`-refusal rule, the audit sites, `domain.LaunchInstance`'s wire shape, and the UI's existing `stopping` rendering. ADR 016 and ADR 017 remain the authorities for ownership and admission; this ADR is subordinate to both.

**Governance:** `Proposed` at publication of this document means implementation NOT STARTED and no approval to start it. The move `Proposed → Accepted` is an Owner decision per [../DEVELOPMENT.md](../DEVELOPMENT.md) §ADR process and will not be made by a tracking edit. The acceptance record for MA-06 F-7 stays **OPEN / BLOCKED BY DESIGN** until the Owner ratifies the design and the implementation slices land.
