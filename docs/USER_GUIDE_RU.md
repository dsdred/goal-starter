## Установка

### Windows

**Вариант A — скачать готовый релиз:**

1. Скачайте архив `goal-VERSION-windows-amd64.zip` с GitHub Releases
2. Распакуйте в любую директорию (например `C:\goal-starter\`)
3. Перейдите в папку через PowerShell

> **SmartScreen:** Выпущенный бинарник не подписан. Windows может показать предупреждение SmartScreen ("Unknown Publisher") при первом запуске. Если вы скачали с официальной страницы [GitHub Releases](https://github.com/dsdred/goal-starter/releases) и проверили SHA-256 по `checksums.txt`, нажмите "Подробнее" → "Запуск в любом случае".

**Вариант B — собрать из исходников:**

```powershell
git clone https://github.com/dsdred/goal-starter.git
cd goal-starter
.\scripts\build-all.ps1
```

Бинарник появится в `bin\goal-windows-amd64.exe`.

### Linux

**Вариант A — скачать готовый релиз:**

1. Скачайте архив `goal-VERSION-linux-amd64.tar.gz` с GitHub Releases
2. Распакуйте: `tar -xzf goal-VERSION-linux-amd64.tar.gz`

**Вариант B — собрать из исходников:**

```bash
git clone https://github.com/dsdred/goal-starter.git
cd goal-starter
GOOS=linux GOARCH=amd64 go build -o bin/goal-linux-amd64 ./cmd/goal
```

## Быстрый старт

```powershell
# 1. Перейдите в папку с бинарником
cd C:\goal-starter   # Windows
cd /opt/goal         # Linux

# 2. Создайте конфигурационный файл
cp goal.example.json goal.json

# 3. Отредактируйте goal.json (см. ниже)

# 4. Запустите
.\goal.exe           # Windows
sudo ./goal          # Linux
```

После запуска GoAl доступен по адресу: **http://127.0.0.1:8088**

> **Примечание:** Если порт 8088 занят, измените `webPort` в `goal.json`.

## Конфигурация

Файл `goal.json` лежит в той же директории, что и бинарник. Он **исключён из git** (содержит секреты и пользовательские пути).

> **Legacy-формат:** `goal.json` использует схему v5 для обратной совместимости. Записи `profiles` при старте становятся **Model** (определениями запуска) GoAl 2.0. Legacy-записи `models` (с `path`) складываются в launch args соответствующей модели. Новые модели, созданные через API или Web UI, используют упрощённый формат GoAl 2.0.

### Полная конфигурация

```json
{
  "version": 2,
  "listenAddress": "127.0.0.1",
  "webPort": 8088,
  "dataDir": "./data",
  "adminUser": "admin",
  "adminPasswordHash": "",
  "authEnabled": false,
  "runtimes": [],
  "models": [],
  "profiles": []
}
```

### Поля конфигурации

| Поле | Описание | По умолчанию | Обязательно |
|------|----------|-------------|-------------|
| `version` | Версия схемы конфигурации | 2 | Нет |
| `listenAddress` | Адрес для HTTP-сервера | `127.0.0.1` | Нет |
| `webPort` | Порт HTTP-сервера | `8088` | Нет |
| `dataDir` | Каталог для хранения данных | `./data` | Нет |
| `adminUser` | Имя администратора | `admin` | Нет |
| `adminPasswordHash` | Bcrypt-хеш пароля администратора (обязателен при `authEnabled=true`; обычно задаётся через настройки Web UI — plaintext не сохраняется) | `""` | Условное |
| `authEnabled` | Включить авторизацию | `false` | Нет |
| `runtimes` | Список AI-рантайнов | `[]` | Нет |
| `models` | Список моделей | `[]` | Нет |
| `profiles` | Список профилей запуска | `[]` | Нет |

### Настройка Runtime

```json
{
  "runtimes": [
    {
      "id": "ollama",
      "name": "Ollama",
      "type": "ollama",
      "executable": "ollama",
      "workingDir": "C:\\Program Files\\Ollama",
      "args": ["serve"],
      "environment": {},
      "healthCheck": {
        "type": "http",
        "url": "http://127.0.0.1:11434"
      },
      "active": true
    }
  ]
}
```

**Поля Runtime:**

| Поле | Описание |
|------|----------|
| `id` | Уникальный идентификатор (латиница, цифры, дефис) |
| `name` | Отображаемое имя |
| `type` | Тип рантайна: `ollama`, `vllm`, `llama.cpp`, `custom` |
| `executable` | Путь к исполняемому файлу |
| `workingDir` | Рабочая директория процесса |
| `args` | Аргументы командной строки |
| `environment` | Переменные окружения процесса |
| `healthCheck` | Настройка проверки здоровья |
| `active` | Активен ли Runtime |

### Настройка модели (legacy-формат `goal.json`)

В `goal.json` модели используют legacy-формат v5. При старте `SeedFromConfig` складывает
`path` и `arguments` в launch args GoAl 2.0 Model, созданной из `profiles`.

**Пример: llama.cpp с GGUF-моделью:**

```json
{
  "models": [
    {
      "id": "qwen35b",
      "name": "Qwen 3.6 35B",
      "runtimeId": "llama-cpp",
      "arguments": [
        "-m", "E:/models/qwen/model.gguf",
        "--mmproj", "E:/models/qwen/mmproj.gguf",
        "--jinja",
        "-c", "200000",
        "--port", "8085",
        "--host", "0.0.0.0"
      ],
      "environment": {}
    }
  ]
}
```

**Вариант B: через path (простой GGUF-файл, складывается в args при старте):**

```json
{
  "models": [
    {
      "id": "llama3",
      "name": "Llama 3",
      "runtimeId": "ollama",
      "path": "E:/models/llama3/model.gguf"
    }
  ]
}
```

При старте `path` превращается в `-m E:/models/llama3/model.gguf` в launch args модели.

**Поля модели (legacy `goal.json`):**

| Поле | Описание |
|------|----------|
| `id` | Уникальный идентификатор |
| `name` | Отображаемое имя |
| `runtimeId` | ID рантайна, где будет запущена |
| `path` | Путь к GGUF-файлу (складывается в args как `-m <путь>` при старте) |
| `arguments` | Массив аргументов командной строки (добавляются к model args) |
| `environment` | Переменные окружения процесса |

### Настройка профиля запуска (legacy-формат `goal.json`)

Записи `profiles` в `goal.json` при старте становятся **Model** GoAl 2.0.
Если `modelId` ссылается на legacy-модель, её `path` и `arguments` складываются
в launch args результирующей модели.

```json
{
  "profiles": [
    {
      "id": "chat-profile",
      "name": "Чат с Llama 3",
      "runtimeId": "ollama",
      "modelId": "llama3",
      "args": ["--port", "8080"],
      "environment": {"OMP_NUM_THREADS": "4"},
      "active": true
    }
  ]
}
```

**Поля профиля (legacy `goal.json` — становится Model при старте):**

| Поле | Описание |
|------|----------|
| `id` | Уникальный идентификатор |
| `name` | Отображаемое имя |
| `runtimeId` | ID рантайна |
| `modelId` | ID модели (опционально) |
| `args` | Дополнительные аргументы командной строки |
| `environment` | Переменные окружения процесса |
| `active` | Активен ли профиль |

### Горячая перезагрузка конфигурации (ADR 009)

После редактирования `goal.json` запросите перезагрузку командой `POST /api/v1/admin/reload` (auth + CSRF; наблюдения за файлом и SIGHUP нет — перезагрузка происходит только по явному запросу).

| Поле | Класс |
|------|-------|
| `logLevel` | hot — применяется сразу при перезагрузке |
| `listenAddress`, `webPort`, `dataDir`, `authEnabled`, `adminUser` | **требуют перезапуска** |
| `adminPasswordHash` | hot только через **Настройки** (смена пароля в UI действует сразу); отредактированный вручную hash применяется при следующем запуске |
| `runtimes`, `models`, `profiles` | только seed — применяются один раз при первом запуске; перезагрузка никогда не повторяет seed |

Ответ перезагрузки показывает, что применено и что ещё требует перезапуска: `{"status":"reloaded","applied":["logLevel"],"restart_required":["webPort"]}`. Если файл некорректен, перезагрузка отклоняется (`400`) и ничего не меняется.

## Веб-интерфейс

После запуска GoAl доступен по адресу: **http://127.0.0.1:8088**

### Возможности веб-интерфейса:

- **Панель управления** — обзор всех экземпляров и их статусов
- **Управление экземплярами** — запуск, остановка, перезапуск
- **CRUD рантайнов** — настройка AI-рантайнов
- **CRUD моделей** — настройка определений запуска (Runtime + аргументы + окружение)
- **История запусков** — персистентные записи завершённых экземпляров (переживают перезапуск)
- **Мониторинг здоровья** — проверка доступности рантайнов
- **Метрики** — встроенные метрики приложения
- **Тема** — System / Dark / Light (нижняя панель сайдбара, сохраняется в localStorage)
- **Язык** — Русский / English (нижняя панель сайдбара, сохраняется в localStorage)
- **Статус соединения с сервером** — индикатор «Сервер» в сайдбаре отражает доступность в реальном времени (зелёный = доступен, красный = недоступен). Если сервер становится недоступен, вверху страницы появляется красная плашка; при восстановлении соединения плашка исчезает и показывается краткое уведомление о восстановлении. Проверка — `GET /api/v1/health` каждые 5 секунд + мгновенная реакция на события offline/online браузера.

### Причина завершения (История запусков)

Колонка «Причина» показывает понятную причину завершения экземпляра:

| Причина | Значение |
|---------|----------|
| Завершен | процесс завершился штатно (код выхода 0) |
| Остановлен | остановлен GoAl (пользовательская остановка, перезапуск или завершение GoAl) |
| Аварийно завершен | аварийное завершение с ненулевым кодом выхода |
| Принудительно остановлен | принудительное завершение (эскалация kill или убийство сироты через действие Kill) |
| Не удалось запустить: … | процесс не запустился; далее идёт ограниченная диагностика |
| Процесс не найден | устаревшая запись: процесса больше нет |
| Идентичность не подтверждена | устаревшая запись: идентичность процесса не подтверждена |
| Отклонено | запись о сироте отклонена (согласована) |

Сырой код выхода никогда не является основной причиной: штатная остановка GoAl
отчитывается кодом управляющего события платформы (3221225786 на Windows, 143 на
Linux), что является нормальной остановкой, а не аварией. Ненулевой код выхода
остаётся доступен как вторичная информация в подсказке («Код выхода: N»).

### Тема и язык

Веб-интерфейс поддерживает две темы (тёмная, светлая) и режим System,
следующий за системной настройкой ОС. Интерфейс доступен на русском и
английском языках. Оба выбора сохраняются в браузере и восстанавливаются
при следующем визите.

Словари переводов находятся в:
- `internal/webui/static/i18n/ru.json`
- `internal/webui/static/i18n/en.json`

Для добавления нового языка создайте JSON-файл с тем же набором ключей
в директории `i18n/` и добавьте элемент `<option>` в `<select>` языка
в `index.html`.

### Авторизация

Если `authEnabled` включён:

1. Перейдите на `http://127.0.0.1:8088`
2. Нажмите **Login**
3. Введите `adminUser` и ваш пароль
4. После входа сессия хранится в HTTP-only cookie

## Управление экземплярами

### Что такое Instance?

- **Model** — настроенное определение запуска (ссылка на Runtime + аргументы + окружение)
- **Instance** — запущенный процесс (runtime entity)

Одна модель может создавать множество экземпляров. Остановка экземпляра не удаляет модель. Перезапуск переиспользует тот же экземпляр: старый процесс останавливается, новый процесс запускается под тем же ID экземпляра. Перезапуск использует **текущую** конфигурацию модели — изменения аргументов, окружения и рантайма, внесённые после первого запуска, применяются при перезапуске (для экземпляров, принадлежащих пайплайну, override-аргументы записи пайплайна продолжают иметь приоритет, всё-или-ничего). Если модель, её рантайм или запись пайплайна больше не существуют, перезапуск завершается ограниченной ошибкой, а не молчаливым запуском старой конфигурации.

**Семантика состояний:** `RUNNING` означает, что дочерний процесс жив. Это **не** гарантия того, что рантайм завершил загрузку модели, что его HTTP-эндпоинт принимает соединения, или что порт не используется другим процессом. GoAl runtime-агностичен и отслеживает только жизненный цикл процесса; готовность рантайма — ответственность внешнего рантайма.

### Процессы-сироты (ORPHAN)

После перезапуска GoAl ранее активный экземпляр, чей процесс, возможно, всё ещё выполняется вне GoAl, отображается как **ORPHAN** («Может выполняться вне GoAl») — на странице «Экземпляры» и на странице моделей (строка модели показывает бейдж Сирота и PID экземпляра; пока экземпляр в состоянии `orphan`, действия Запустить/Остановить/Перезапустить не предлагаются, чтобы случайно не запустить вторую копию модели). Доступны два действия:

- **Отклонить (Dismiss)** — безопасная согласованность: запись переходит в `stale`, но процесс **не затрагивается**. Используйте, если уверены, что процесс уже остановлен или вы остановите его сами.
- **Завершить (Kill)** — деструктивное действие: действительно завершает процесс-сироту. В Web UI требуется явное подтверждение. Перед каждым сигналом GoAl повторно проверяет идентичность процесса (исполняемый файл + время запуска); если идентичность нельзя подтвердить, завершение отклоняется и сирота остаётся в списке (повторная попытка или Отклонить). На Windows процесс завершается немедленно; на Linux сначала выполняется штатное завершение (5 с), затем принудительное. Если процесса уже нет, запись согласовывается без отправки сигналов.

Завершение — только явное действие пользователя; GoAl никогда не завершает процессы автоматически.

### Управление через CLI

```bash
# Список всех экземпляров
curl http://127.0.0.1:8088/api/v1/instances

# Статус конкретного экземпляра
curl http://127.0.0.1:8088/api/v1/instances/INSTANCE_ID

# Остановить экземпляр
curl -X POST http://127.0.0.1:8088/api/v1/instances/INSTANCE_ID/stop

# Перезапустить экземпляр
curl -X POST http://127.0.0.1:8088/api/v1/instances/INSTANCE_ID/restart
```

## Модели

**Модель** — настроенное определение запуска: ссылка на Runtime, аргументы запуска
и окружение. Все параметры запуска (`--host`, `--port`, `-m`, `--mmproj` и др.)
задаются через аргументы. Физические файлы моделей (GGUF, MMProj) не являются
отдельными сущностями — это обычные аргументы запуска.

**Синтаксис поля аргументов.** Поле аргументов (в мастере модели и в «Свои»
аргументах пайплайна) — это командная строка. Она разбивается на отдельные
токены по пробельным символам; заключите токен в двойные кавычки, чтобы
внутренние пробелы остались в одном аргументе (например
`-m "E:\models\my model.gguf"`). Внутри двойных кавычек обратный слэш экранирует
следующий символ — `\"` становится литеральной `"`, а `\\` — литеральным `\`, —
поэтому JSON-значения проходят без искажений: например
`--chat-template-kwargs "{\"reasoning_effort\":\"medium\"}"` передаётся рантайму
как один аргумент `{"reasoning_effort":"medium"}`. Вне кавычек обратный слэш —
литеральный символ, так что пути Windows вида `E:\models\m.gguf` сохраняются как
введено. Точно те же правила применяются и к аргументам модели, и к «Своим»
аргументам записи пайплайна.

### Переменные в конфигурации

GoAl разрешает ссылки `${VAR}` в аргументах, путях к исполняемым файлам,
рабочих каталогах и значениях переменных окружения в момент **запуска/перезапуска**
(не при сохранении). Это делает конфигурации переносимыми между машинами.

**Встроенная:** `${GOAL_DATA}` — абсолютный путь к каталогу данных GoAl.

**Окружение процесса:** `${MY_VAR}` — значение из окружения процесса GoAl.

**Экранирование:** `$${GOAL_DATA}` даёт литеральный текст `${GOAL_DATA}`.

**Примеры:**

```
# Аргументы модели (переносимо между машинами):
-m ${GOAL_DATA}/models/my-model.gguf --port 8080

# Исполняемый файл рантайма:
${GOAL_DATA}/bin/llama-server

# Значение переменной окружения:
HF_HOME=${GOAL_DATA}/hf-cache
```

**Поведение:**

- **Preview / Start / Restart** разрешают переменные из *текущего* окружения процесса.
- **Restart** подхватывает изменения окружения: если после запуска с `MY_VAR=A` вы поставили `MY_VAR=B`, Restart использует `B`.
- **Неопределённая** `${MISSING}` или **некорректная** `${123}` ссылка отказывает в запуске с понятной диагностикой.
- **Без рекурсии:** если `A` равно `${B}`, то `${A}` даёт литеральный текст `${B}` (не значение B).
- **Export/Import** конфигураций **пока недоступен**.

### Переменные окружения

**Когда использовать:** Поле «Переменные окружения» предназначено для
конфигурации, которую запускаемый runtime-процесс или его зависимости читают
из ОС-окружения, а не из командной строки. Используйте его, если runtime
(или подключённая библиотека) ожидает настройку через переменную окружения,
а не через `--flag`. Обычные параметры запуска задаются в Args.

**Семантика:**

- Переменные передаются дочернему процессу при запуске. Дочерний процесс
  наследует окружение родительского процесса GoAl; переменные уровня
  runtime и уровня модели переопределяют родительские значения
  (модель переопределяет runtime).
- Это **не** аргументы командной строки и **не** макросы/подстановки
  внутри Args. Это отдельный канал передачи.
- Значения **write-only**: API принимает их при создании/обновлении,
  но никогда не возвращает клиенту. Мастер редактирования модели
  отображает существующие ключи без раскрытия значений. Непринятый
  ключ сохраняется без изменений. Замена значения требует явного
  ввода нового значения. Удаление переменной требует удаления строки.

**Пример:**

```
CUDA_VISIBLE_DEVICES=0,1
HF_HOME=D:\cache\huggingface
```

GoAl не интерпретирует и не валидирует эти значения — они передаются
дочернему процессу как есть. Действует ли конкретная переменная,
полностью определяется внешним runtime и его зависимостями.

### Пример: llama.cpp с Qwen GGUF

Типичная конфигурация модели llama.cpp:

```bash

  -H "Content-Type: application/json" \
  -d '{
    "id": "qwen-35b",
    "name": "Qwen 3.6 35B",
    "runtime_id": "llama-cpp",
    "args": ["-m", "E:\\models\\qwen\\Qwen.gguf", "--mmproj", "E:\\models\\qwen\\mmproj.gguf", "-ngl", "99", "-c", "131072", "--host", "127.0.0.1", "--port", "8085"],
    "active": true
  }'
```

Резолюция команды:
`llama-server -m E:\models\qwen\Qwen.gguf --mmproj E:\models\qwen\mmproj.gguf -ngl 99 -c 131072 --host 127.0.0.1 --port 8085`

### Preview команды запуска

## Пайплайны

**Пайплайн** — это упорядоченная группа существующих моделей, которые запускаются,
останавливаются и перезапускаются вместе. Пайплайн — это *запускатель* над вашими
моделями: он не создаёт новых моделей и не хранит собственные параметры запуска.

**Повторяемые записи.** Одна и та же модель может входить в пайплайн **несколько раз** как
независимые записи (напр. `Qwen3.8-27B` с `--port 8081` и снова с `--port 8082`). Каждая
запись — отдельный запуск со своей идентичностью; порядок списка = порядок запуска.

**Режим аргументов записи (всё-или-ничего, явный).** Для каждой записи выбирается один из
двух режимов в компактном сегментированном контроле: **Из модели** (используются аргументы
модели) или **Свои** (textarea с пометкой «Аргументы модели полностью заменяются»).
Свои аргументы — это полный список аргументов запуска, который **полностью заменяет**
аргументы модели для этой записи (без слияния и дополнения); две записи одной модели могут
запускаться с разными аргументами. Режим применяется только при запуске; сохранённые
аргументы модели никогда не изменяются. История запусков показывает ровно то, что
запускалось, включая замены.

**Групповой жизненный цикл (по записям).**
- **Старт** запускает записи в порядке списка, последовательно и best-effort: сбой на одной
  записи не останавливает остальные и не откатывает уже запущенные. Запись даёт
  `already-running`, если у модели уже есть активный экземпляр, принадлежащий другому
  пайплайну или запущенный вручную — пайплайн никогда не забирает чужой экземпляр. Внутри
  одного пайплайна две записи одной модели запускают два независимых экземпляра. Запись, у
  чьей модели последний экземпляр — `orphan`, пропускается (`orphan-skipped`).
- **Стоп** останавливает только те экземпляры, которые запустил пайплайн, по записям, в
  **обратном** порядке. Вручную запущенные экземпляры той же модели не трогаются.
- **Перезапуск** = обратный стоп, затем обязательный прямой старт всех записей.
- В списке **inline-панель иконок** (как на странице моделей): остановлен — Старт + Изменить + Удалить;
  запущен — Перезапустить + Стоп + Изменить + Удалить.
  Столбец **Состояние** агрегирует живые состояния записей (running / starting / stopping /
  failed / orphan / stopped), повторяющаяся модель отображается по разу на запись
  с собственным состоянием.

**Автозапуск (отдельно от кнопки «Старт»).** У пайплайна есть переключатель **Active**
(«Автостарт пайплайна»). Это *настройка только для запуска GoAl* — она не влияет на
ручное действие **Старт**. При старте GoAl `Active`-пайплайны запускают **все** свои
записи (до model-level автозапуска), поэтому модель, покрытая обоими механизмами,
получает экземпляры, принадлежащие пайплайну. (Legacy per-entry поле `AutoStart`
сохраняется в хранилище для совместимости, но больше не влияет на запуск.)

**Целостность (без неявного каскада).** Удаление модели, на которую ссылается пайплайн,
возвращает конфликт — сначала отредактируйте или удалите пайплайн. Структурные изменения
(добавить/убрать/переставить записи) и удаление отклоняются конфликтом, пока у пайплайна
есть активные собственные экземпляры; имя, аргументы и `Active` можно менять всегда.

**Через веб-интерфейс:**
1. Перейдите в раздел **Пайплайны**
2. Нажмите **+ Создать пайплайн**
3. Введите имя, при необходимости включите **Автостарт пайплайна**, и для каждого блока
    выберите модель и режим аргументов (**Из модели** / **Свои**); блоки выстраиваются
    сверху вниз в порядке запуска — добавляйте кнопкой **+ Добавить модель**, меняйте
    порядок кнопками ↑/↓ (× убирает блок)
4. **Старт / Стоп / Перезапуск / Изменить / Удалить** действуют на всю группу через
    inline-иконки; пер-записные статусные чипы и столбец **Состояние** показывают
    running/stopped/orphan

## Портативная конфигурация (экспорт / импорт)

Экспортируйте и импортируйте рантаймы, модели и пайплайны в виде одного JSON-файла.

### Web UI

Перейдите в **Настройки → Переносимая конфигурация**.

**Экспорт:**
1. Выберите область: **Всё** (по умолчанию), **Runtime**, **Модель** или **Пайплайн**.
2. При выборе конкретной области укажите сущность в выпадающем списке.
3. Нажмите **Скачать**. Браузер сохранит `goal-portable-config.json`.

**Импорт:**
1. Нажмите на выбор файла и выберите файл `goal-portable-config.json`.
2. Нажмите **Проверить** (dry-run). UI покажет количество сущностей или детали конфликтов.
3. Если проверка прошла, нажмите **Импорт** и подтвердите в диалоге.
4. Импортированные сущности сразу появятся в UI.

Тот же API доступен через `curl` для автоматизации:

### Экспорт (API)

```bash
# Экспортировать всё
curl -b "goal_session=..." -o goal-portable-config.json \
  "http://127.0.0.1:8088/api/v1/export"

# Экспортировать одну модель (включая её рантайм)
curl -b "goal_session=..." -o goal-portable-config.json \
  "http://127.0.0.1:8088/api/v1/export?model_id=your-model-id"
```

Скачанный файл называется `goal-portable-config.json`. Содержит полную зависимость (closure) выбранного корня.

**Безопасность:**
- **Значения** переменных окружения НЕ экспортируются. Экспортируются только **имена ключей** (`environment_keys`) как справочная метаданные.
- **Args моделей экспортируются без изменений** и могут содержать конфиденциальные данные (API-ключи, токены в аргументах командной строки). **Проверяйте Args перед отправкой файла.**

### Импорт

```bash
# Пробный запуск (валидация + проверка коллизий, без изменений)
curl -b "goal_session=..." -X POST \
  "http://127.0.0.1:8088/api/v1/import?dry_run=true" \
  -d @goal-portable-config.json

# Реальный импорт
curl -b "goal_session=..." -X POST -H "X-CSRF-Token: <token>" \
  "http://127.0.0.1:8088/api/v1/import" \
  -d @goal-portable-config.json
```

**Поведение импорта:**
- Экспортированный JSON-файл можно напрямую использовать как тело POST-запроса.
- Импорт **не перезаписывает** существующие сущности. При коллизии ID или имени рантайма весь импорт отклоняется (HTTP 409).
- Импорт **атомарен**: либо создаются все сущности, либо ни одна.
- Импорт **не запускает** модели и пайплайны сразу. Сохранённые флаги `Active`/`AutoStart` применяются при следующем обычном запуске сервера.
- `environment_keys` в бандле являются справочными и НЕ восстанавливаются как записи Environment на целевой машине.
- Переменные (`${VAR}`) проверяются на синтаксис. Неопределённые переменные принимаются (будут разрешены при запуске на целевой машине).
- Максимальный размер файла: 10 MiB.
- Dry-run носит справочный характер: изменения репозитория между dry-run и реальным импортом могут привести к ошибке 409.

## Безопасность

### Текущие настройки безопасности

| Параметр | Значение |
|----------|---------|
| Аутентификация | HTTP-only cookies, session-based |
| CSRF защита | Да, для всех unsafe методов |
| Rate limiting | Login: 100 запросов/мин с одного адреса клиента → HTTP 429 |
| Limit request body | http.MaxBytesReader |
| Bind по умолчанию | 127.0.0.1 (localhost) |

### Настройка для внешней сети

Чтобы сделать GoAl доступным по сети:

1. Откройте `goal.json`
2. Измените `listenAddress` на `"0.0.0.0"`
3. Включите авторизацию: `"authEnabled": true`
4. Перезапустите GoAl
5. Задайте пароль через **Settings → Server** в Web UI (сохраняется как `adminPasswordHash`)

```json
{
  "listenAddress": "0.0.0.0",
  "webPort": 8088,
  "authEnabled": true,
  "adminUser": "admin",
  "adminPasswordHash": "$2a$12$..."
}
```

### Журнал аудита безопасности

GoAl фиксирует действия, связанные с безопасностью, в устойчивом журнале аудита: `<dataDir>/goal_audit.jsonl` (по одной JSON-строке на событие). Записываются: входы в систему (успех/неуспех/ограничение частоты), выход, сохранение настроек (только имена изменённых полей; смена пароля фиксируется флагом `password_changed` — сам пароль никогда не записывается), а также start/stop/restart/dismiss/kill/cleanup инстансов.

Каждая строка содержит метку времени, имя события, пользователя (или пользователя, попытавшегося войти), TCP-адрес клиента и небольшой detail-блок (только идентификаторы). В файле **никогда** нет паролей, session/CSRF-токенов и значений переменных окружения.

- **Чтение напрямую:** `tail goal_audit.jsonl`, `grep login.failure goal_audit.jsonl` и т. п.
- **Запрос через API:** `GET /api/v1/admin/audit` (нужна аутентифицированная сессия), необязательные параметры `limit` (по умолчанию 100, максимум 1000), `offset` и точный фильтр `event`; события возвращаются от новых к старым.
- **Хранение:** файл ротатируется при 10 MiB, хранится не более 3 поколений (максимум ~30 MiB). Настройке в первом выпуске не подвергается.
- **Резервные копии:** включайте `goal_audit.jsonl*` в резервные копии `dataDir`.

## Установка как сервис (Linux systemd)

### Ручная установка

```bash
# 1. Скопируйте бинарник

# 2. Создайте конфигурацию

sudo systemctl enable goal

sudo systemctl status goal
```

```bash
sudo journalctl -u goal -f
```

### Обновление сервиса

```bash
sudo systemctl stop goal
# замените бинарник
sudo cp goal /opt/goal/goal
sudo systemctl start goal
```

## Windows-сервис (встроенный, `goal --service`)

GoAl регистрирует себя как полноценный Windows-сервис из того же бинарника
(без внешних скриптов; [ADR 011](adr/011-windows-service.md)). `goal --service …`
доступен только на Windows; на Linux жизненный циклом владеет systemd
(`deploy/systemd/goal.service`), а команда выводит ограниченную ошибку
"not supported".

### Установка сервиса (требуется Administrator)

```powershell
# 1. Скопируйте бинарник и конфиг в стабильное место, например C:\GoAl
# 2. Создайте каталог dataDir и goal.json с АБСОЛЮТНЫМ существующим dataDir (и абсолютными путями рантаймов)
# 3. Установите (от Administrator)
goal.exe --service install --config "C:\GoAl\goal.json"

# 4. Запустите (установка НЕ запускает сервис)
goal.exe --service start
```

- Имя сервиса по умолчанию `GoAl` (сменить через `--service-name`), display name
  "GoAl - Local AI Runtime Manager", аккаунт **LocalSystem**, тип старта `auto`
  при загрузке (`--start manual` для отключения), таймаут остановки SCM 45 с.
- **Установка отказывается** (ничего не записывается), если конфиг не проходит
  загрузку и валидацию, если эффективный `dataDir` — относительный путь **или
  не существует** (установка никогда не создаёт его), если `workingDirectory`
  какого-либо рантайма (в конфиге или в существующем `goal_repo.json`) или
  path модели (в конфиге) — относительный путь, либо если `executable`
  рантайма не является сервисно-безопасным. `executable` безопасен, если он —
  абсолютный путь, **либо** если он относительный, а его `workingDirectory` —
  абсолютный каталог, в котором этот исполняемый файл существует: сервис тогда
  запускает склеенный абсолютный путь ровно так же, как обычный запуск
  (например, `executable: llama-server.exe` +
  `workingDirectory: C:\tools\llamacpp\b10519` принимается и запускает
  `C:\tools\llamacpp\b10519\llama-server.exe`). Относительный `executable` с
  пустым или относительным `workingDirectory`, либо со склеенным путём, которого
  не существует, — отказ: рабочий каталог сервиса —
  `C:\Windows\System32`, поэтому такие пути невозможно однозначно
  детерминировать. Установка никогда не переписывает сохранённые значения.
- Повторная установка с тем же образом — идемпотентный no-op; другой образ
  (exe, конфиг или аргументы) — отказ, сначала выполните uninstall.

### Управление сервисом

```powershell
goal.exe --service status     # состояние SCM, PID, uptime
goal.exe --service stop       # корректно: StopPending -> Stopped (<= 30 с)
goal.exe --service start
goal.exe --service restart    # Stop -> ожидание Stopped -> Start -> ожидание Running
```

### Удаление сервиса

```powershell
goal.exe --service uninstall
```

Удаление сначала выполняет корректную остановку, затем снимает регистрацию.
Пользовательские данные (конфиг, репозиторий, аудит, логи) не затрагиваются.

### Замечания по сервисному режиму

- Сервис выполняет то же самое приложение, что и foreground-режим: Web UI на
  заданном порту, инстансы, автостарт и аудит (`goal_audit.jsonl`) работают
  идентично. Web UI — основной интерфейс.
- Операционные логи в сервисном режиме пишутся в **Event Log Windows**
  (Application, источник `GoAl`), в foreground-режиме — в stdout. Аудит-файл
  никогда не дублируется в Event Log.
- **Аккаунт LocalSystem:** у сервиса нет интерактивного профиля пользователя.
  Всё, что сервис использует (конфиг, `dataDir`, рантаймы, модели), должно
  быть доступно LocalSystem; расположение под `C:\Users\<user>\…` для сервиса
  не поддерживается.
- Остановка занимает не более неизменного 30-секундного бюджета приложения
  (с запасом внутри 45-секундного таймаута SCM). Жёсткое убийство сверх этого
  оставляет тот же принятый остаток, что и в foreground (orphans/stale
  согласуются при следующем запуске).

## Миграция

При обновлении с GoAl v1.x файл `goal_repo.json` автоматически мигрируется до текущей схемы (v8) при первом запуске:

| Legacy (v5) | Текущая (v8) |
|-------------|--------------|
| Записи `profiles` | Становятся `models` (определения запуска) |
| Записи `models` (физические GGUF) | Складываются в launch args модели (например, `-m <путь>`) |
| `profile_id` в инстансах | Переименовывается в `model_id` |
| История запусков | Сохраняется без изменений |

Резолюция команды запуска идентична до и после миграции. Действия пользователя не требуются.

## FAQ

### Где хранятся данные?

Данные хранятся в `dataDir` из конфигурации (по умолчанию `./data`). Файл репозитория: `goal_repo.json`. Предыдущая версия каждого JSON-файла состояния (`goal_repo.json`, `goal.json`) хранится как `<file>.bak` (одно поколение) — это позволяет откатиться при повреждении или ошибке записи.

### Как сменить порт?

Измените `webPort` в `goal.json` и перезапустите GoAl.

### Как сменить адрес?

Измените `listenAddress` в `goal.json` и перезапустите GoAl.

### Что означает статус "stale"?

Процесс был перезапущен ОС, но GoAl не может восстановить состояние. Нужно перезапустить вручную.

### Как сбросить пароль администратора?

Задайте новый пароль через **Settings → Server** в Web UI (вступает в силу немедленно, сохраняется как `adminPasswordHash`). Либо запишите валидный bcrypt-хеш в `adminPasswordHash` в `goal.json` и перезапустите GoAl.

### Где логи самого GoAl?

Логи выводятся в stdout/stderr. Для systemd: `journalctl -u goal`. Для Windows — Event Log.

### Как кросс-компилировать?

```powershell
# Windows -> Linux
$env:GOOS='linux'; $env:GOARCH='amd64'; go build -o goal-linux ./cmd/goal
```

### Как проверить целостность бинарника?

```bash
# Проверьте SHA256 из checksums.txt
Get-FileHash bin/goal-windows-amd64.exe -Algorithm SHA256
```

### Как обновить GoAl?

1. Скачайте новую версию
2. Остановите текущий процесс
3. Замените бинарник
4. Перезапустите

Конфигурация `goal.json` и данные в `dataDir` не меняются.

### Как запустить несколько экземпляров GoAl?

Каждый экземпляр должен иметь свой `goal.json` с разными `webPort` и `dataDir`:

```powershell
$env:GOAL_CONFIG = "C:\goal-instance-1\goal.json"
.\goal.exe

$env:GOAL_CONFIG = "C:\goal-instance-2\goal.json"
.\goal.exe
