# GoAl v2.3.0 — Release Notes (EN)

GoAl v2.3.0 is an intermediate release with two new capabilities: **resource monitoring**
(CPU / RAM / GPU / per-process RAM) and the **unified Commands API** for lifecycle control.
Accepted by the Owner manually on 2026-11-24 (v2.3.0-rc2: all 8 checks of the per-component
actions and process visibility PASSED on real Windows hardware).

## Resource monitoring (ADR 025 / ADR 026)

**API (read-only, no control actions):**

- `GET /api/v1/system/gpu` — NVIDIA telemetry via `nvidia-smi` (ADR 025, RES-02A): for each
  GPU — model, driver, VRAM total/used/free. NVIDIA only; read-only.
- `GET /api/v1/system/resources` — universal monitoring (ADR 026, RES-03A/03B): a vendor-neutral
  model with a three-level capability declaration per metric — `supported` (static fact),
  `available` (source detected in this request), `sampled` (value obtained in this request).
  Providers: `system` (CPU/RAM) and `nvidia` (VRAM). Values are sampled once per request:
  no background polling, no cache, no "last good" value. A failure of one source does not
  invalidate the others: the response state is
  `ok` / `partial` / `unavailable` / `measurement_failed`.
- **System CPU/RAM** (RES-03B): RAM total/available/used (the `used` value is computed,
  marked `estimated`), logical core count, CPU utilization (two counters in a ~250 ms window
  inside the request). Works on Windows and Linux; on macOS — RAM only (`available` via
  `vm_stat`, estimated) with capability headroom.
- **Per-process RAM (RSS)** (RES-05A/06, ADR 026 A-026-1): in `processes[]` of the
  `GET /api/v1/system/resources` response — the RSS of each instance process in a
  non-terminal state (`starting` / `running` / `stopping` / `orphan`), attributed to the
  instance / model / runtime / pipeline element. An unavailable value carries a reason
  (`pid_not_assigned`, `process_exited`, `identity_mismatch`, `identity_unconfirmed`,
  `counter_unavailable`), never a fabricated "0". Terminal processes are absent from the list.
  The metric is not supported on macOS.

**Interface:**

- New **"Resources"** page (in the "Additional" section): CPU load and core count, RAM
  total/used/available and percentage, one card per GPU (vendor, model, driver, memory class,
  VRAM total/used/free and percentage); a CPU-only setup is shown as a normal state; a
  measured "0" is distinguished from "no data". Refresh is manual and every 5 seconds,
  **only while the page is open** (leaving the page stops the polling).
- **Per-process RAM on the "Resources" page** (RES-06): cards of live processes with RSS and
  attribution to the model/pipeline; after a process stops, its card disappears.
- **RU localization of the "Resources" page** completed: "Рантайм" (Runtime), "ОЗУ процесса"
  (Process RAM), "Видеопамять: всего/используется/свободно" (VRAM: total/used/free), binary
  units ГиБ/МиБ/КиБ (GiB/MiB/KiB), the decimal separator follows the locale (comma in RU).
  An explanatory note under the processes section: the resident memory of a process may
  include shared pages and memory-mapped model files. Metric values, unit thresholds (1024)
  and calculations are unchanged; the EN dictionary is preserved.

## Commands (ADR 024, Stage 1)

- A single control point `POST /api/v1/commands/execute` (authentication + CSRF). A dictionary
  of nine commands: `model.start` / `model.stop` / `model.restart`, `instance.start` /
  `instance.stop` / `instance.restart`, `pipeline.start` / `pipeline.stop` / `pipeline.restart`.
- Commands delegate to the existing lifecycle paths (ADR 017, the unified arbitrator): the
  commands create no second process-control mechanism and do not change state semantics.
- UI: per-component **Start / Stop / Restart** on the pipeline element chips (G3-RES-01 UI,
  ADR 024 D-11/D-12); stop and restart are available for the precisely attributed running
  component, start — for a cleanly finished (`exited` / `failed`) component of the same
  pipeline.

## Fixes

- **Per-component Start/Stop/Restart persist across pipeline restarts** (`9059e4d`, ADR 024
  refinement, 2026-11-24): after the second and later "start → stop" cycles, the pipeline
  element chip showed only the information icon again — selecting an instance required exactly
  one history record, although history is retained forever by contract. Now, under precise
  attribution, a running component shows Stop/Restart and a finished component — Start; with
  several active components of one record, control is intentionally unavailable (no arbitrary
  process choice). Pipeline-level commands and backend command semantics are unchanged.
  Accepted by the Owner in the v2.3.0-rc2 manual acceptance (2026-11-24).
- Commands test stabilization: synchronization of the mock instance store (mutex) — a race in
  the test infrastructure removed (`53d1ef4`).
- Sidebar test synchronized with the new section count after "Resources" was added (`36dba42`).
- Documentation: copy-safe configuration examples (no mojibake on copy) in the configuration
  guide (`4579325`); ROADMAP/BACKLOG status reconciliation after the Stage 1 publications
  (`a8f8f3e`, `2e4b8d4`).

## Platform limitations

- **GPU:** only NVIDIA is supported via `nvidia-smi` (driver and the utility must be present).
  AMD / Intel / Apple GPU providers are not implemented. A missing `nvidia-smi` is a normal
  `unavailable`; a driver error is a bounded reason; a measurement failure does not change
  declared-supported.
- **Per-process RAM:** Windows and Linux (Linux: verify→read→re-verify via /proc).
  **macOS — not supported** (the metric is declared unsupported). Precise process attribution
  to an instance requires a match of the executable file and start time (±5 s tolerance); an
  unconfirmed identity is never presented as a fact.
- **CPU/RAM:** Windows / Linux — measured; macOS — RAM with an estimated `available`
  (`vm_stat`). CPU utilization adds a fixed window (~250 ms) to the request time.
- **Binaries are unsigned** (Authenticode is not configured): Windows SmartScreen may warn
  about the unsigned executable.

## Known limitations

- **C-7 (ADR 026):** real NVIDIA telemetry was visually confirmed by the Owner on a host with
  two RTX 5060 Ti GPUs (Owner screenshots, v2.3.0-rc2 manual acceptance, 2026-11-24); see the
  dated post-release correction below for the closure.
- **macOS:** acceptance on a real macOS machine was not performed (the build is
  cross-platform; testing was done on Windows/Linux machines).
- **Per-component VRAM** (RES-02B, attributing VRAM to individual instances) is not in this
  release; resource limits, scheduling and priorities are out of scope (ADR 015 is frozen).
- Some ROADMAP/BACKLOG checkboxes on the resource track remain open until the release
  reconciliation (RES-03 — until the macOS acceptance and C-7; RES-04 — until the Owner
  acceptance record); see the dated post-release correction below.

- Integrity check: `sha256sum -c checksums.txt` (or compare against the table above).
- **Upgrade (safe order):**
  1. Back up the data directory (`dataDir`) — it contains `goal_repo.json`, the `.bak` backup, and user data.
  2. Stop the running instances, then stop GoAl (the binary cannot be replaced under a running process).
  3. Replace the binary with the new version.
  4. Start GoAl.
- The data directory (`dataDir`) and `goal_repo.json` are not modified; automatic schema
  migration runs at first startup.
- **Background launch:** Windows — `goal --service install` (as administrator, ADR 011);
  Linux — `deploy/systemd/goal.service`.
