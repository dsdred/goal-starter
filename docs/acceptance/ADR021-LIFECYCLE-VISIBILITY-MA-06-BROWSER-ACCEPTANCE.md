## 1 Scope and objective

**Objective.** A real backend `stopping` state must become observable through the existing API and the existing Web UI during the interval in which the managed process is still alive, and must converge to the correct terminal state afterwards — without changing synchronous `Stop`, without changing persistence ordering, and without any client-side fabrication.

**In scope:** manual stop of a running instance (UI and API), pipeline-initiated stop, the terminal convergence that follows, the recovery classes that a stop can be confused with (`orphan`, `stale`), repeated-stop safety, and concurrent lifecycle arbitration around a stopping instance.

**Explicitly out of scope:** the HTTP status code and body shape of `Stop` (unchanged — `docs/API.md:119`, `:159-163`, `:174-191`; the one-in-flight-per-model rule at `:157` also stays as written); the arbitration state table (ADR 017); durable lifecycle ownership (ADR 016); the five findings registered as **OS-1 … OS-5** in [ADR 021 §Out-of-scope findings](../adr/021-lifecycle-state-observability-view.md), which are tracked separately and must not be fixed inside an F-7 slice — OS-4 (`ShutdownWithPersistence` holding `s.mu.RLock` across `Snapshot()` and the store write, `supervisor.go:937-946`) and OS-5 (`Manager.Stop` may be re-invoked by a second `Stop` after the stop context expires) were registered by Gate 24af; any latency bound on `GET /api/v1/instances`; and **pipeline aggregation**, whose endpoint state table and per-entry projection are not modified by F-7 (RV-7).

## F-7.5 correlation and dwell requirements (Gate 24ag, RV-8)

**The five facts.** F-7.5 is met only when all five of the following are recorded for the **same stop operation**, and the report lists them as five separate lines with their own evidence, not as one narrative claim:

1. the API returned `stopping` (F-7.1/F-7.2 or F-7.3);
2. the managed OS process was still alive during the observation, proven by **process identity** (F-7.2), not by a bare alive-PID check;
3. the browser **received** `stopping` in a response body (F-7.4);
4. the browser **rendered** the real badge from that response (F-7.5);
5. all of the above fall inside one controlled stop interval — the interval bounded by the stop request and the observed termination (F-7.6).

**Correlation, not simultaneity.** The requirement is that the observations belong to one interval, never that they share one instant: a state read, an identity read and a paint are different events, and demanding a single timestamp would make the criterion unmeetable. What makes them one observation set is the binding below.

**Timestamp / correlation rule (excludes a post-termination false PASS).** A run records, in this order, and each line must be present with its value:

- `t0` — stop request issued (client action, or server receipt captured from the response);
- `t1` — API response body containing `stopping`, with the instance ID and the run's `PID`;
- `t2` — process-identity check of that PID: `GetProcessIdentity` result compared to the instance's frozen `Executable` (`domain/instance.go:107`) and, where `HasStartTime` is true, to the run's `StartedAt`;
- `t3` — browser network record for the response consumed by the rendered row (URL, response body state, response timestamp);
- `t4` — DOM/screenshot capture of the badge, with the same instance identifier visible in the captured row;
- `t5` — termination evidence (F-7.6): the PID gone or identity no longer matching, plus the terminal state.

The set passes only if `t0 < t1 ≤ t2 < t5` **and** `t0 < t3 ≤ t4 < t5`. If `t2` cannot be ordered before `t5` — or `t4` sits after it — the observation describes a **post-mortem** state and the criterion is FAIL or NOT OBSERVED, never PASS. A badge seen only after the process exited proves rendering, not visibility-while-alive, and does not satisfy F-7.5. Inferring liveness from a stale PID value or from a process listing taken before `t0` is expressly inadmissible.

**Dwell, and how a short window is handled.** The UI refreshes every 3000 ms (`app.js:2358-2364`), so a real stopping window materially shorter than the poll period can legitimately be missed. That case is a measurement limitation, not a product defect:

- **A missed polling interval must not be classified as a product FAIL.** It is recorded as **NOT OBSERVED** (§16) with the window duration and poll period both stated.
- **The controlled acceptance fixture must provide a sufficiently long real `stopping` interval** so a human and a 3000 ms poll can both land inside it. Per ADR 021 §Test-only stop gate obligation **T-9**, the dwell comes from the fake runtime's own shutdown behavior (the `manager.Stop` grace window is 5 s before `ForceKill`, `manager.go:242`, capped by the 15 s stop context, `supervisor.go:1576`) — from the fixture, never from production. **Whether any available fixture behavior can actually produce such an interval on Windows is NOT YET PROVEN (Gate 24ah AH-4):** the requirement below is therefore a prerequisite, not a satisfied condition. The dwell must be **demonstrated by measurement in a separately authorized preparation gate before an Owner UI leg is scheduled**; no existing fake-runtime mode may be assumed sufficient (`fake.go:166-170` returns on the first signal, `:172-188` is signal-dependent in a way Windows does not match, `:190-206` never waits for a stop signal); a dedicated **test-only** fixture behavior may be required; and any such behavior must drive the **real OS process lifecycle** and must never fabricate or inject a `stopping` API response, so the process-identity liveness requirement of F-7.2 stays intact. Where `GenerateConsoleCtrlEvent` fails and `GracefulStop` escalates immediately to `ForceKill` (`internal/platform/platform_windows.go:110-122`), a useful `stopping` interval may not exist in that run at all, and an unobserved badge there is **NOT OBSERVED / INCONCLUSIVE**, never a product FAIL.
- **No artificial production dwell.** No `sleep`, no widened timeout, no injected delay in `internal/process` or `internal/platform` may be added to make the leg observable; that would test a state the shipped product never produces.
- **A timeout or missing observation is reported distinctly from a proven incorrect state.** `NOT OBSERVED` (window too short, poll missed, browser tab lost, capture failed) is never written as FAIL (`state observed wrong`), and neither is written as BLOCKED without naming the blocker.

**Owner-driven UI evidence is preserved.** Facts 3–5 above are agent-collected *backend and repository* evidence; they supplement and never replace the Owner's own observation of the badge. See the global actor rule in §Execution constraints (**RV-9**): no browser criterion may be marked PASS on agent-driven UI activity.

## Execution constraints (contract items 12-14, detail)

- **Global actor rule (RV-9) — applies to every browser criterion, not only the manual leg.** The **Owner** performs the lifecycle action in a real browser and states what was seen; the **agent** may collect only the permitted backend and repository evidence around it (API/store/audit responses, process-identity checks, network records read from the Owner's session, DOM captures, CI logs, byte measurements). Agent-driven browser interaction — navigating, filling, clicking a state-changing control, or driving a headless browser as a stand-in — **must not replace mandatory Owner UI observation and never yields a PASS on a UI criterion**. Where the Owner did not observe it, the criterion is BLOCKED or NOT OBSERVED.
- **Manual Stop leg (12):** must be run by the Owner in a real browser against a binary whose provenance is bound to the published SHA. The agent's role is measuring the resulting bytes.
- **Pipeline Stop leg (13):** requires a pipeline with at least one entry whose model can be started and stopped; the stop must be initiated through the pipeline path, not the model path. The `stopping` **observation** for this leg is taken on `GET /api/v1/instances` / `/instances/{id}` and in the instance/model/pipeline-chip rendering — **not** on `GET /api/v1/pipelines/{id}`, which cannot report a live `stopping` (RV-7, F-7.12). Pipeline aggregation code is not modified for this leg.
- **Fixture dwell leg:** the acceptance binary must be built from the published SHA with no F-7-specific production timing change; the stopping dwell comes from the fake runtime (T-9). If the published build cannot yield a window that a 3000 ms poll can land in, that is a fixture gap to report, not a reason to widen production timeouts. **Sequencing prerequisite (AH-4):** the dwell must first be *demonstrated* — by measurement, on the platform the leg runs on, in a separately authorized preparation gate — and only then may an Owner UI leg be scheduled. Scheduling a human observation against an assumed window is not permitted: it would produce a NOT OBSERVED or a post-mortem reading and would look like an attempt. This gate writes no fixture and prescribes no fixture shape.
- **Platform leg (14):** local `-race` is unavailable on the acceptance workstation, so F-7.13's race evidence is CI-only and must be quoted verbatim from the Linux job. A same-SHA rerun, if one is ever authorized, must be reported as such: the rerun attempt number and which job re-executed are part of the evidence, and no attempt-1 failure may be restated as green.
- **Seam-free binary for the human leg:** the test-only stop gate (ADR 021 §Test-only stop gate) may make deterministic Go tests possible; it is **not** admissible for the Owner's manual/pipeline browser legs, which must observe the shipped timing behavior.

## 15 Evidence classification

Every row of the final report must carry exactly one class:

- **[O] Owner observation** — what the Owner saw and stated (badge visible, dialog behavior). Never a substitute for a byte measurement, and never sufficient for a PASS on its own. Conversely, a browser criterion is **never** met by an agent-driven UI action: the Owner-observed half is mandatory, not optional (**RV-9**).
- **[A] Agent-observed fact** — a measurement taken by the agent against a running instance or a job log (response bodies, network records, CI job output, recount of raw `PASS |` / `FAIL |` lines). A liveness claim under this class **is a process-identity check**, not a bare PID-exists check: it must name the executable path compared and, where the platform supplies a start time, the start time compared (`recovery.go:5-9`, `:18-20`).
- **[C] Repository-derived conclusion** — derived from committed bytes (code paths, invariants, line references at a named SHA).

Rules: browser-suite totals are recounted as raw `PASS |` / `FAIL |` lines, never as the arithmetic sum of printed `TOTAL` lines; classes are never merged into a single narrative claim; a criterion whose only evidence is [C] proves the mechanism, never the observation; and a criterion whose only evidence is [O] proves the experience, never the backend state — F-7.5 requires both plus the [A] correlation lines of §"F-7.5 correlation and dwell requirements".

## 16 PASS / FAIL / BLOCKED / NOT OBSERVED criteria

- **PASS (per criterion)** — the required observation is recorded, bound to a named SHA and to a retained artifact, with every admissible evidence class present, and with the `t0…t5` ordering of §"F-7.5 correlation and dwell requirements" satisfied for the F-7.1…F-7.5 chain.
- **FAIL** — the observation was attempted **inside a window that was long enough to observe** and the required state was not produced or not visible (for example the API returns `stopping` only after PID death, or the UI jumps `running` → `exited`). A FAIL asserts that the product behaved wrongly.
- **NOT OBSERVED** *(added for Gate 24ag, RV-8; extended for Gate 24ah AH-4)* — the attempt was made but the measurement could not land: the stopping window was shorter than the poll/observation capability, the response or capture was lost, the session was interrupted, a required timestamp could not be ordered, **or the platform gave no graceful dwell to observe** — on Windows a failed `GenerateConsoleCtrlEvent` escalates straight to `ForceKill` (`internal/platform/platform_windows.go:118-122`), so the run legitimately has no live `stopping` interval for a 3000 ms poll to land in. **NOT OBSERVED is not a product failure and must never be recorded as one**; it names the measurement gap, states the observed window duration (or states that the signal-delivery path produced none, with the platform and the delivery outcome) and the 3000 ms poll period, and leaves the criterion unmet.
- **BLOCKED** — a precondition outside this program prevents the attempt (design not ratified, no implementation published, no binary with bound provenance, the observation window unreachable by a human without the test-only seam, **the fixture dwell capability not yet demonstrated on the target platform (AH-4)**, or the environment unavailable). **BLOCKED is not PASS, not FAIL and not NOT OBSERVED, and it never closes the criterion.**
- **Overall F-7 leg** — **PASS** only when F-7.1…F-7.14 are all PASS; **FAIL** if any criterion FAILs; otherwise **INCONCLUSIVE**, with each criterion that is not PASS listed under its own disposition (`NOT OBSERVED` or `BLOCKED`) and its named blocker or measurement gap. `NOT OBSERVED` on a browser criterion keeps the leg open in exactly the same way `BLOCKED` does: neither is downgraded to a PASS, and neither is upgraded to a product FAIL.
- **Closure of `LIFECYCLE-VIS-01`** — an Owner decision, taken separately from this evidence, as with every finding in this program. Evidence never closes a task by itself.
